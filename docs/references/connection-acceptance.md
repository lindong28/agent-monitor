# Device connection acceptance

Use this development entry when changing the account page's device pairing, exit preview, confirmation or connector lifecycle. It uses six synthetic accounts and controlled loopback services. It never logs in, queries quota or sends provider account messages. Product runtime does not depend on a harness checkout.

Prerequisites: the project's installed `.venv`, Node with built-in WebSocket support (24 or later), an installed Chrome, and the installed `agent-browser` task adapter with its private CLI and sibling `test-chrome.mjs` test launcher. The browser tool is an explicit development input; obtain its path from the local `agent-browser` skill. The default Chrome executable is the macOS Chrome Dev application; pass `--browser` for another installed executable. No browser is downloaded and no daily browser profile is used. The shared test launcher owns the fresh Chrome HOME/profile, mock keychain and basic password store, bounded sanitized startup diagnostics and process-group cleanup; these settings must not be applied to a daily browser profile. Startup failure does not retry. Headless does not prove that macOS cannot display a keychain dialog; if desktop interference is reported, stop the owned test and correlate its printed PID/start time before another launch. On macOS the temporary HOME uses a short `/tmp` path because the CLI socket has a 103-byte path limit. The owned headless target is brought to the foreground within that headless instance, and readiness requires six accounts to have loaded; the product intentionally defers account loading in hidden tabs.

```sh
node scripts/accept_device_connection.mjs --browser-tool /absolute/path/to/browser-task.mjs
node scripts/accept_device_connection.mjs --browser-tool /absolute/path/to/browser-task.mjs --launchd
```

The default command checks the actual account panel and CSS: primary action pairs and previews, the China address and warning are red, cancelling sends zero batches, refreshing requires a new pairing, explicit confirmation sends exactly one six-account fixture batch, and pairing error or cancellation does not send another batch. It uses an isolated HOME, browser profile, target binding and random service ports. The fixture substitutes loopback pairing ports in the served module; it does not change installed product source. Browser clicks use explicit postconditions; missing CLI receipts must not cause repeated clicks. Before each next click, a read through the same native session checks that its control is ready. Popup postconditions can already be true while native commands still take time to settle: a confirmation-read measured 27099 ms in the local Chrome Dev run. This is a test observation, not a product latency target or a proven explanation of the native daemon internals.

`--launchd` additionally requires an active macOS GUI login. It creates a uniquely named `com.agent-monitor.acceptance.*` job from the production launch definition, with an isolated worker command, HOME, state and dynamic pair port. The worker executes `client_connector.main` with the resolver replaced by the existing controlled bridge fixture. It checks loading, connector readiness, 262144-byte transfer, KeepAlive replacement, unloading, recorded worker/bridge process exit and observed listener closure separately. A second run injects failure after readiness and checks cleanup. The formal `com.agent-monitor.connector` job and port 39002 are not managed by this entry. Existing `tests/test_connector_service.py` tests retain coverage of installer ownership refusal and configuration handling.

The runner prints each completed check and exits nonzero on failure. Observation budgets constrain the test, not product readiness or shutdown SLAs. Cleanup failure retains the isolated job identity and directory for diagnosis; a passing bootout receipt alone is not a shutdown result. If no worker identity was captured after bootstrap, cleanup remains unverified and its directory is retained. Temporary fixture data contains no real account credentials. Tests do not cover real provider behavior, Chrome system-proxy resolution, login/reboot, visible desktop focus or non-macOS service management.

Decision: [f8c3](../adr/20261024-f8c3-connection-acceptance-entry.md). Related unit suites: `test_device_connection.py`, `test_connector_service.py`, `test_client_network.py`.

Acceptance on 2026-10-24: the documented combined command exited 0 on the MacBook, using macOS, one installed Chrome Dev version, six synthetic accounts, two preview/cancel-or-confirm rounds, and ready/error/silent pairing outcomes. The final fixture count was one six-account batch; the error and cancellation paths added no preview or batch. Both address and warning colors were checked. Two isolated LaunchAgent runs covered normal restart/unload and failure after readiness; recorded workers/bridges exited and temporary files were removed. A separate SIGTERM check used a sleeping browser substitute plus the actual isolated fixture: the runner exited nonzero, the owned substitute exited, and its HOME was removed. Twenty tests in `test_connector_service.py`, `test_device_connection.py` and `test_client_network.py` also passed under an isolated HOME. These readings do not establish another browser version, real provider interaction, or that no desktop keychain prompt is visible to the user.

Test-launcher update on 2026-10-24: the shared launcher was exercised through this six-account browser entry on the MacBook, with preview/cancel, refresh/confirm and error/silent pairing paths passing. `node --test scripts/accept_device_connection.test.mjs` injects both browser startup and cleanup failure and verifies that the fixture process still exits, its isolated HOME is removed, and both failures remain visible. The user reported no recurring keychain prompt during the 10:15–10:18 local acceptance window. This is a bounded observation, not attribution of the original popup or a guarantee against future macOS dialogs. The LaunchAgent implementation was unchanged and was not rerun for this test-launcher change.
