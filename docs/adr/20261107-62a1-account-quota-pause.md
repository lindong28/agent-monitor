# Isolate a verified revoked quota credential during batch refresh

Accepted after one independent L1 decision review. A quota-only batch must retain each failed account's operation and continue independent accounts when the owning client's response reliably identifies a revoked credential. It must retain the existing shared pause for ambiguous or shared failures. This changes failure scope, not request concurrency, routing, retry budgets or authorization.

Reuse the existing Controls JSON primitive in an account-identity namespace beneath `state/upstream_controls/accounts/`. Classify only `account/rateLimits/read` failures with the official client's wrapped HTTP 401, exact structured `token_revoked`, coherent body status and unchanged full local identity and access-token digest immediately before and after the failed RPC. The diagnostic parser alone is not admission authority. A body-only 401, conflicting transport status, credential change or unverified identity retains shared protection. This is a narrow credential rejection classification, not a claim about account bans or permanent refresh-token invalidity.

Keep the global provider lane and acquire it before the selected account control. Known account-local failures do not stop independent batch items. Ordinary managed and native quota consumers respect the account hold and rejected credential aliases. Retain non-reversible access-token digests after clearing the selected pause so that another profile containing the old credential does not retry it. The history contains no credential value or upstream body and has no time-based automatic release. Duplicate rejection of the same digest does not grow the record. Explicit login may replace that rejected credential but cannot bypass unrelated restrictions.

Preserve the existing bounded authentication refresh, explicit device reauthorization and local commit of an already obtained candidate. Add optional `pause_scope=account` and a canonical managed profile to the existing recovery endpoint; omission retains legacy machine-wide behavior. Bind status, confirmation, request, operation and receipt to the selected scope. Recovering one account never clears another account or a shared pause. The accounts page reuses its recovery panel through a per-account “修复登录” action, rather than requiring manual pause removal or creating another login flow.

Existing global pauses remain in place and are not silently migrated or cleared. Existing cached observations, original failures, restrictions, request sequencing and Monitor routing remain authoritative. The added files belong to the existing locked, owner-only controls state family; no separate registry, database, scheduled job or credential export is added. A downgrade to a version unaware of these account controls does not preserve the new account isolation: retain the current version while account holds or rejected credentials are in use.

Protect a pause-bound original operation before preparing ordinary work, including batches submitted by older clients. A batch's preparation failure restores already prepared members while their profile locks remain held. A later quota-only batch skips paused members without replacing their failure. If a scoped recovery also raises a shared pause, both protections remain; the existing manual shared-pause acknowledgement is presented only as an operator step after investigating its cause. It performs no upstream request and does not clear the account pause. Both status views expose the account pause through safe account metadata, so the page explains this state without creating another recovery mode or retry budget.

Acceptance uses isolated synthetic stdio peers and real HTTP/browser consumers. It covers multiple local failures followed by success, rejected aliases and process reload, ambiguous/shared counterexamples, scope binding, legacy global recovery and the existing bounded recovery paths. Synthetic results do not establish current provider availability or authorize extra live authentication or quota requests.
