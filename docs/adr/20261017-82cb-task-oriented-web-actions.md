# Task-oriented Web actions

The product review follows the existing personal-monitor tasks in `docs/product-spec.md`: compare quota before choosing an account, drill from aggregate usage to retained evidence, and distinguish a refresh from a new send. The definition remains an alignment draft; this change does not add team administration or alter accounting.

Keep the quota comparison before the account panel. Name row navigation “账号操作” and provide an explicit quota query beside it. Retain the panel's batch progress and per-account results. Move the Guide status refresh into its status section, name network refresh “重新检测”, and name Overview, Explore and Sessions refresh “更新统计与配额”: all three force paths also request quota. Keep Explore's five presets, show the matching preset/custom state, and expose dates without opening advanced controls. Chart drilldowns describe their destinations. Session evidence toggles name their content; manual pagination returns to the usage heading, while background refresh does not move the reader.

Preserve contract G4i's reset of provider, search, window and ordering; name it “重置筛选与排序” and hide it only when all controls are at defaults. The initially proposed filter-only reset was rejected because it would change that existing contract without a specific user decision.

Extend explicit new rounds to a selected set using the existing batch mechanism. `batch-start` accepts optional `profile_ids`: omission retains legacy eligible-account behavior; a supplied list must be nonempty, unique and entirely eligible. Freeze both the selected IDs and `expected_batch_id` before confirmation and submit that same snapshot, including when all accounts are selected. A single-account send is an explicitly confirmed new batch with one member. This extends the all-account default in [the original batch decision](20261007-b923-codex-account-batches.md), preserving its CAS, fixed membership, all-operations-idle requirement and definitely-unsent-only retry. Do not remove the individual-start guard or infer a reset cycle.

Before publishing a new manifest, retain the previous published batch operation for any excluded members in their existing `batch_result` slot, under the catalog and profile locks. Copy only an operation belonging to the currently published batch, keep the operation itself, and do not promote an orphan. A retention or preparation failure must leave the old manifest and dispatch nothing. Selected members continue through existing preparation. This prevents a later quota-only refresh from erasing an excluded member's last send result; it does not create an unbounded batch history. Show retained results with their own time, not as the current round.

Alternatives were label-only changes, a new account drawer, and allowing individual starts to bypass the batch guard. The selected approach reuses existing action/result consumers and the batch lifecycle, while the alternatives either leave the task discontinuity or split duplicate-send protection across paths. No snapshot schema, machine/account identity, provider message, concurrency bound or scheduled work changes.

Validation separates synthetic HTTP/app-server send counts, result retention and rejection paths from real deployed browser navigation and read-only interactions. Real provider sends, login and deletion are not executed for this review. Production revision and browser results are recorded separately after deployment. The decision received one independent review; its original packet, findings and raw page observations are retained under `/Users/lindong/task-artifacts/monitor-ux-improve-20261017/`.
