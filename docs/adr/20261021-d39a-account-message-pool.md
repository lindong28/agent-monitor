# Codex account message pool

Accepted 2026-10-21 after one independent decision review and a targeted compatibility check against main `53da9c5`. The user requested 100 predefined everyday messages and an appropriate per-account selection algorithm.

Each explicit send selects one of 100 unique Chinese short messages with `secrets.choice`. Entries have equal probability; accounts and rounds draw independently, so repeats are allowed. A shuffle bag would require shared selection state to enforce a property the user did not request; a fixed account hash would repeatedly select the same message. The pool is source-controlled in `codex_messages.py`.

After existing identity, quota, request-pause and restricted-thread checks, save the selected text in `operation.message` in the same atomic profile update that marks the send unknown, before transmitting that exact field. This records selection, not proof of delivery. Retain existing operation/batch retention and outcome semantics. Quota-only and login-only actions do not draw. Old records without the field remain valid and are not backfilled. The list API's existing top-level `message` string becomes a pool description; `operation.message` is the selected text. The UI preserves selected text in retained batch details.

This supersedes only the fixed-message content in [c814](20261007-c814-codex-account-actions.md) and [b923](20261007-b923-codex-account-batches.md). The current [request controls](20261021-a84c-codex-request-controls.md) and [persistent upstream pauses](20261021-6bd2-upstream-prevention.md) remain in force. No extra provider calls, automatic sends, retries, tools or output-content collection are introduced; the existing brief OK response instruction remains. Random text is a content feature, not evidence of reduced provider risk.

Storage remains the private atomic JSON profile: one short field per retained operation, no growing history or new database. Selection happens once per send, with no additional disk write or network request. Local acceptance uses synthetic stdio accounts and the isolated browser fixture; actual provider sends, answer quality and production behavior are not established by those checks.

Local validation: 138 related tests passed, including 100-entry uniqueness, two accounts across two rounds, and success/disconnection outcomes. The isolated browser exercised one synthetic send, a quota-only refresh and a page reload at two viewport widths (1280 and 390 pixels); no real provider requests were made. Independent change review found that a new batch hid the retained previous message. A failing DOM regression reproduced it; rendering retained and current batch operations separately with operation-id deduplication fixed both new-batch failure and success states. The 52-test Web suite passed after the fix.
