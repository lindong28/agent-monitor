# Retain successful Codex quota observations

Status: accepted for local implementation, 2026-10-08, after one independent decision review. Deployment and real-account verification remain separate.

The user requested automatic quota refresh after sending messages, because historical accounts still showed old reset countdowns. The sending path already queries `account/rateLimits/read` after successful completion. A subsequent operation can replace a non-batch operation's successful reading, and a failed query then leaves the display with only older machine observations. This explains a possible loss path, not proof that any particular earlier send succeeded or failed.

Retain one optional `last_quota` observation in each private account profile. It contains the existing complete quota reading and its original `observed_at`, without credentials or inferred reset times. Successful post-send and quota-only queries update it atomically with their operation record. Before replacing an operation, retain the newest available observation from the old operation, retained batch result and `last_quota`. Failed, cancelled or pending operations do not erase that reading or advance its observation time. A newer successful response with unknown fields replaces the entire old reading.

The existing account API exposes this optional profile field. Both the account card and overview projection select the newest observation across it and the legacy operation/batch fields. Workspace plus email identity, whole-reading selection, machine tie precedence, batch message authority and historical deletion CAS remain unchanged. This extends a62e's original API scope to preserve a reading independently of replaceable operations; snapshot export and account memory remain unchanged.

Alternatives were retaining all operations (unnecessary history growth), copying old results into a new operation (misrepresents that operation), and writing Web readings into machine account memory (mixes provenance). The selected change adds no provider request, retry, message or scheduled job. Already lost readings cannot be reconstructed; an authorized successful query is still needed to obtain a current reading.

Scope and assurance: local account-reading retention and its existing consumers, A0/V1; reversible local changes with one change reviewer for persistent state and display semantics. Targeted tests first reproduced loss after a failed refresh and a renderer fallback to old machine data. Use isolated synthetic credentials and stdio peers for regression tests; do not treat them as evidence of a real provider reset cycle.

Local validation: 58 Codex tests, 29 quota tests and 39 Web static tests passed. The new retention cases cover legacy operation and batch sources, failed queries, newer successful responses with unknown reset, and Manager reconstruction. One independent change reviewer reran the 16 account-action tests and the quota-renderer test and reported no findings. An isolated browser exercised the real page, HTTP handler and Manager against the synthetic stdio peer with two emails sharing one workspace: each single send automatically queried quota and updated its card and historical row; a subsequent query failure and page reload retained the successful reading. Actual synthetic sends remained two. The two send-to-visible-result samples were 1.042 and 1.043 seconds, including operation polling; these are fixture timings, not provider latency. This does not verify real credentials, service deployment or any real account's current reset time.
