# Reuse Sessions results from unchanged admitted sources

Accepted 2026-10-19 after one independent decision review. The user requested faster visible, usable Sessions lists while preserving functionality, accounting and freshness. Production browser baselines were 4.623 seconds for a cold-browser 30-day list and 4.517 seconds with a warm browser; these are individual samples, not an SLA. See the [execution record](../plans/20261019-sessions-performance.md).

Keep normal synchronization, admission, complete event validation, ancestry resolution and Python aggregation. Reuse each source's completed list rows and filter choices only when its admitted path and nonempty file signature, time window and semantic query match. Check current admission before consulting the cache; never retain a generation lease in it. Source changes invalidate that source independently. Detail and standalone readers retain their existing behavior.

For moving windows, bind the exact start and UTC end date. Cache only when every candidate event returned by the reader is no later than the original end; accept reuse only while the end moves forward within that same key. A future candidate prevents caching, a clock rollback rejects reuse, and calendar changes change the key. Fixed custom windows bind both exact endpoints; all-history has no time boundary. Preserve query value order and first-value semantics. Synchronization and final global sorting still run on hits.

Store JSON-encoded results in a process-local LRU bounded to eight entries and 8MiB encoded content, with a short dictionary lock and independent decoded response objects. Oversized results remain readable without caching. This is not an RSS bound. There is no TTL, persistence, background preparation or additional thread. Concurrent misses may compute independently; no slow query runs under the cache lock.

Directory normalization also runs once per distinct source project, and each complete read reuses successful validation of adjacent identical usage metadata, including amount nullness. Scalar validation remains per event. These reduce first-read costs without removing field validation.

Direct SQL projection was rejected: a live lease and valid digest do not prove complete statistics validation on the direct first-publication path. The complete reader remains the boundary. SQL aggregation would alter arithmetic/relationship implementation; full-event caching retains substantially more data; background preparation adds lifecycle and publication work; process parallelism adds workers and memory. This result cache reduces repeated work while retaining a bounded, reversible implementation.

This supplements the index decision b4d8 and preserves c6b2 conversation semantics and 97cd publication boundaries. It does not promise constant-time cold reads: cold/new-generation materialization still scales with matching events. Validate complete response equivalence, signature/query/time invalidation, independent responses, bounded retention and real browser cold/warm/new-generation behavior before delivery. Rollback requires only compatible source deployment and process replacement, with no data migration.

Implementation tuning, 2026-10-19: the fixed production corpus measured 4,896,609 / 5,701,221 / 75,962 / 54 encoded bytes per source for all-history. The initial 8MiB limit caused alternating eviction and repeated complete reads (8.799s cold, 9.179s repeat). Increase only the encoded-content bound to 16MiB, keeping eight entries and all invalidation/validation behavior. This reversible local capacity adjustment is L0; it adds at most 8MiB retained encoded content and does not change freshness or accounting. Current architecture and tests use the revised bound; the original reviewed decision above remains historical.
