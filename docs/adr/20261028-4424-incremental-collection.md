# Persist incremental collection work

Accepted for implementation on 2026-10-28 after one independent decision review. This changes deterministic execution and cache invalidation, preserving the existing accounting policies.

Collection currently decodes retained history and every cached file, prices all events, and rebuilds aggregates even when no source changed. A fixed ten-file synthetic workload at 1,000/10,000 retained events used 0.016847/0.178399 CPU seconds for unchanged collection; collection plus validated export used 0.045278/0.450557 seconds. These are single samples per state and size, not production capacity measurements.

Keep raw observations authoritative in the existing SQLite archive. Persist normalized source observations and dirty event keys; atomically update priced/project-attributed observations and aggregate contributions. Scheduled rollup consumes complete prepared buckets, preserving the existing legacy/date authority and crash replay rules. Full-history readers and snapshot export retain their output contracts. Pricing, provenance, project blockers/identity and calculation-version changes invalidate derived state. Missing source files never remove retained facts; metadata/account transforms still run independently of usage changes.

An in-process cache would be lost by periodic CLI processes. Faster pricing or JSON alone keeps repeated historical work. Lower cadence changes freshness, and a watcher or append cursor alone leaves downstream full-history costs. A separate service adds lifecycle/transaction boundaries without a requirement. Reuse SQLite and the existing lock order, keep token_cost.py unchanged, and introduce no new provider requests, service, retention rule or snapshot schema.

Source discovery and headers remain proportional to source/session count. Changed files are reparsed completely to preserve historical edits, completion and ancestry semantics; no append-only guarantee is assumed. Complete bucket reconciliation remains proportional to bucket count, and complete export/validation remains proportional to its output. These residuals must be measured separately before claiming whole-task improvement.

Normalized file caches replace JSON arrays with version-marked cache signatures; older code must miss rather than trust empty compatibility payloads. Raw changes, including writes by older code after rollback, must leave persistent dirty keys. Re-upgrade after old writes and source deletion must replay retained facts. Initialization/invalidation may rebuild from retained raw data; code rollback must not delete authoritative archive or legacy rollup data. Repeated rounds replace derived rows rather than accumulating generations.

Verification compares existing accounting outputs and operation counts across history sizes, unchanged/changed rounds, restarts, source corrections/removal, pricing/project invalidation and transaction failure. Preserve ordered duplicate winners, Claude monotone completion/conflict errors, unknown versus zero costs, empty-bucket removal and same-batch export consistency. Implementation, production benefits and rollback behavior remain unverified at decision time.

## Storage audit and proposed follow-up

A read-only local audit on 2026-10-28 at code revision `b0b3e2065fa3e0ae88ef5ab7a5c35fbfc4264d62` found a 1,195,122,688-byte archive. SQLite `dbstat` attributed about 470.7 MB to prepared events and their primary-key index, 381.4 MB to raw events and their indexes, and 228.5 MB to per-file observations and their indexes (decimal MB). The compact aggregate buckets and their index occupied about 0.82 MB. `freelist_count * page_size` was about 93.3 MB; these pages are reusable inside the database, not additional retained facts. These are point-in-time readings during live collection, not a growth rate or an exact reclaim estimate.

The authoritative raw observations preserve historical accounting after original logs disappear; their retention is unchanged. Per-file observations are parser/replay state, removed when a source disappears and replaced when it changes. Prepared events and buckets are derived state invalidated by calculation, pricing and attribution changes; they replace existing rows rather than retaining successive generations. The present archive does not contain transcript bodies. Deleting historical raw observations or substituting only daily totals would change detail/export and correction capabilities and is not part of the proposed engineering repair.

The prepared-event representation is unnecessarily broad: it serializes the complete UsageEntry, repeating raw identifiers, timestamps, model and counters. A bounded sample of the first and last 500 dedup keys contained 733,373 bytes of prepared JSON; compact serialization used 691,373 bytes and only fields differing from raw used 279,055 bytes. This is a nonrandom 1,000-row sample, not an implemented schema, whole-database forecast or proof that a plain overlay is sufficient. Incremental correction must retain the previous bucket keys and contribution vector independently of the current raw row, because archive triggers can run after the old raw value has already been replaced or deleted. The recommended first repair is a minimal previous-contribution record plus derived fields/provenance; complete event readers can join raw facts with the derived overlay.

A second candidate is normalizing source paths and repeated event identities into compact internal keys. Per-file observations currently repeat the path in each row and in indexes; a full column-length query found about 21.8 million path characters before counting index copies. Preserve lexical path winner order, distinct conflicting observations, source-removal behavior and rollback compatibility. Exact payload deduplication can be considered only if its reference-count and recovery cost is justified; merely sharing an event key does not make observations equivalent.

Physical compaction is a separate maintenance step after the representation migration. The archive connection uses no automatic vacuum; the snapshot exporter's VACUUM INTO applies to the rollup snapshot, not this archive. Free pages can be reused by subsequent writes, so do not compact on each scan. A supported archive maintenance/migration entry point should coordinate existing writers/readers, verify sufficient temporary space and a recoverable source, preserve late writes, validate accounting and recovery, and then report actual filesystem bytes. No live deletion, compaction, schema change or retention change was performed by this audit.

These are proposed follow-up repairs, owned by the next authorized Agent Monitor storage implementation. First preserve the incremental work bound while reducing duplicated representation, then compact once if worthwhile; do not use a TTL or whole-cache eviction that recreates full historical work every scan. Validation should compare the same input snapshot's event details, buckets and diagnostics before/after, cover corrections/deletions, old writers, pricing/attribution invalidation and recovery, and measure both warm CPU and data/index/free-page bytes across history sizes. Actual savings, migration duration and peak disk usage remain unmeasured. This audit corrects the earlier assumption that the observed cache size was a necessary cost of incremental collection.
