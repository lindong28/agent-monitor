# Explicit managed authentication recovery

Accepted after one independent L1 review, seven criteria accepted. The user authorized repairing the current quota failure through Agent Monitor. Normal quota reads and the existing single-query recovery retain their contracts; this decision adds a distinct, explicitly confirmed operation rather than expanding an old confirmation.

For a current managed Monitor profile whose bound pause records a quota-read HTTP 401/token_revoked, offer **刷新认证并检查配额**. The existing recovery endpoint accepts an optional `mode=renew_auth`; its distinct `quota-auth-recovery` action and mode-bearing approval scope prevent reuse of a quota-only confirmation. The owning machine, full identity, profile, pause, route bridge, provider lease and profile lock remain authoritative.

Within the existing cumulative child deadline, request `account/read(refreshToken=true)` once using file credentials from the bound CODEX_HOME. Only a changed access token belonging to the same identity permits one quota read. Do not repeat the known failed usage request before requesting new credentials. Missing refresh credentials, unchanged credentials, identity change, transport failure or deadline exhaustion stop the operation. Keep the first refusal and safe refresh-stage evidence. New credentials are a candidate, not proof of upstream acceptance. Only a valid saved quota observation can clear the matching pause.

Managed recovery reuses the managed-account environment whitelist and forces ChatGPT file authentication. Parent API keys, alternate access tokens and parent Codex configuration are excluded; the same selected Monitor route is retained. A matching auth file alone cannot establish the identity actually selected by a child that inherits alternate authentication inputs.

The official [App Server authentication documentation](https://developers.openai.com/codex/app-server#auth-endpoints) defines managed force refresh. Fixed Codex 0.166.0 source at `6ff1e1ca3b30fc8b914720681fcf5fe62e95f856`, notably `account_processor/workspace_routing.rs:258`, discards its result before reading account information. Routing and startup prewarming can perform further HTTP/OAuth operations. One explicit refresh RPC is not a one-HTTP or one-OAuth guarantee; the Monitor deadline and child cleanup bound execution. Do not infer permanent credential failure or mandatory login from this ambiguous RPC. Request reset-credit details only where consumed; this operation does not consume them.

Alternatives: automatically expanding all old queries changes their approval contract; repeating an unchanged rejected credential provides no new recovery evidence; forcing login is not yet justified; hand-written OAuth or borrowed credentials changes ownership and bypasses the supported client. A separate service, credential store or approval mechanism is unnecessary. Reuse the existing recovery receipt and state lifecycle; do not change RateLimits or snapshot schemas.

Offline acceptance must exercise the new action/scope boundary, known failure versus unknown refusals, credential change and identity rejection, accumulated deadline and process cleanup, diagnostic readback, saved quota consumption, and unchanged quota-only behavior. Real-account restoration remains a separately approved verification and is not established by the source analysis or isolated tests.

The new failure stages occur only during an explicitly requested foreground operation. Its HTTP/CLI result, retained recovery receipt and existing pause surface expose failure synchronously; no new background job or alert transport is introduced. This preserves the current diagnostic storage and retention boundaries. The state response advertises this action only for a bound failed or interrupted, known-unsent quota operation, so it does not relabel a successful message operation as a failed query.

Real verification returned `no_new_credentials`: the official refresh did not confirm a changed token, so Monitor did not query quota and retained the pause. The recovery card presents that known outcome directly and does not offer an unchanged-credential quota retry. This does not prove permanent refresh-token invalidation or that login is mandatory. The managed refresh child now drains stderr without blocking its cumulative deadline, keeps at most the first 64 KiB in memory, and saves a credential-redacted excerpt of at most 512 characters in the existing recovery receipt. A credential cut at the input limit is also redacted. This is client diagnostic text, not an upstream error classification or proof of refresh success; no raw log or additional provider call is retained or introduced. Earlier attempts have no such excerpt and remain explicitly unverified as to the refresh cause.

After this known outcome, a distinct `reauthorize` mode and `quota-login-recovery` confirmation can prepare official device authorization on the account-owning Hub itself. Its scope includes the full account, managed profile and original quota operation; the expected value remains the current pause. Ordinary login and old confirmations retain their contracts. The recovery card advertises this option only when its bound failed, known-unsent quota task and current recovery receipt match. The CLI quota-only endpoint rejects this asynchronous mode. Other source nodes do not advertise it.

The existing account Manager owns the asynchronous operation, cancellation, login serialization and limits. It retains the original quota operation and preceding recovery receipt in the new operation before starting; job memory is not the sole record. One provider probe lease retains the pause while initializing the official client, requesting one device code and waiting for the matching completion. Only this explicit mode skips the old account/read prerequisite. Completion failure or unknown, cancellation, wrong identity or no changed credentials stops without quota or a new device code; a failed completion may already have saved credentials and does not authorize deleting them. A successful completion must pass the existing email/workspace checks and persist changed credentials before one quota read. No model turn is used.

After closing the client, the same profile lock and provider lease protect publication of the valid quota cache and restoration of the original quota operation ID and batch result. A current valid window is required, not merely a numeric used percentage. The already obtained reading also enters the Hub's existing machine_quota publication consumed by QuotaView; writing quota_snapshot alone is insufficient. That publication holds its condition through local commit and restores its previous record if commit fails. Candidate account/control state is separate from the live authorization operation and lease; only a saved successful control state replaces the live state. Failed local commit retains the original operation/recovery chain and candidate observation, reports a local persistence/publication failure and offers no new upstream retry. This is bounded local compensation, not an atomic transaction across files or a guarantee against process/power failure at every instruction.

The owning lease validates its pause/probe and active identity under the provider lock. After the valid reading, account result and normal consumer publication are saved, one successful control write records recovery (including its predecessor), removes the matching pause and active marker, and records release time. The final close only releases its lock; it does not perform a second terminal save that could leave an interrupted active marker. It does not re-enter Controls.resume or the separately locking quota-recovery helper. Independent account holds retain their existing permission-based behavior. Device confirmation waits at most the existing 600 seconds; initialization, code request, identity, quota and cleanup have their existing separate bounded phases. This is not a 600-second total deadline or a count of HTTP/OAuth requests. The same-machine provider lane is occupied during authorization, and the confirmation explains that cost. Real execution still requires a new, specific approval and the person's official authorization; local implementation and tests do not establish account restoration.
