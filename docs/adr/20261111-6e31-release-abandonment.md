# Explicit topology release abandonment

Accepted after one independent L1 decision review on 2026-11-11. The operator requested a public release-coordination CLI after a fixed release was blocked by a node whose primary checkout had advanced.

Use `service release status [--id ID] [--json]` to read local records without Git, topology or network checks. Use `service release abandon --id ID --expect FULL_SHA --reason TEXT` on the clean primary Hub checkout to explicitly terminate an incomplete release. Reuse the topology lock and node release primitive; require the original target-to-SSH mapping and matching reservation identities. Do not roll back source, restart services or deploy a replacement. Automatic version substitution and rolling back shared main were rejected because they change intent or history.

Before remote actions, archive the complete original record in `state/release-history/ID.json` and persist abandonment progress. The current release record remains resume authority; archive writes precede current writes, so interrupted persistence can safely repeat a matching, idempotent release. Refuse conflicting archives or records before releasing anything. Unknown or missing node records are errors; only a consistent first-inspection failure can be marked never reserved. Completed releases, including unfinished completion cleanup, retain their existing cleanup path. Deployment remains blocked while abandonment is incomplete, including after changing to a single-node topology.

Each explicit abandonment adds one small history record for audit and recovery, retained without automatic expiry; no periodic writer or new database is introduced. The existing JSON/flock storage is sufficient for one cooperative coordinator. CLI failures are immediately visible through per-node output and nonzero exit, so no background alerting is added. At decision acceptance implementation, interruption recovery, public CLI and deployed operation were unverified.
