# One-click Codex account batches

Status: accepted for local implementation, 2026-10-07, after one independent decision review and clarification. Extends [c814](20261007-c814-codex-account-actions.md); deployment and real-account acceptance remain separate.

The user approved one click to send the fixed message to every account already added to this page, persistent batch progress, credential reuse, independent reauthorization, and no blind resend after a lost response. The batch is an explicit user action, not an inferred reset cycle or a weekly scheduler. A distinct next-round button explicitly sends again to all currently saved accounts. Server reset observations remain separate from message completion.

Publish a current batch manifest containing its ID, creation time and fixed profile IDs. Serialize creation, expected-current-ID comparison, retry and individual starts with the catalog file lock. Prepare every profile's queued operation before publishing the manifest, and dispatch only after publication. Stale creation requests return the current batch without dispatch. New rounds require all operations to be idle. Only explicit retry may resume terminal not-sent items; succeeded, failed-after-send and unknown items are never retried in that batch. Individual sends cannot bypass this rule for current batch members.

The active operation remains authoritative in the profile record. Before another operation replaces a completed current-batch operation, move its result into the profile's batch_result slot in the same atomic JSON write. Only an operation matching the published manifest may replace that slot; an orphan from interrupted preparation must not erase the published batch's result. The manifest references those records rather than duplicating mutable results. GET recovers interrupted state but never dispatches work. Recovery rereads under the profile lock before changing state. Persist unknown before transmitting, preserving c814's lost-acknowledgement rule. Quota-only refresh has its own latest operation and preserves the batch's message result.

Use up to eight concurrent checking/sending operations for these independent I/O tasks. Device authorization waits release a progression slot and reacquire it after authorization, so they cannot occupy all sending slots. Login and sending retain existing deadlines, and queued work can be cancelled. Eight is an implementation bound, not a measured performance guarantee. Waiting device authorization can retain one subprocess per account. Results and errors are visible in the click-triggered page; no unattended worker or push-alert channel is added.

Browser-only loops were rejected because they lose durable batch identity on refresh. Local seven-day deduplication was rejected because it is not evidence of a provider reset cycle. Automatic scheduling is outside the approved page workflow. The existing identity, credential-isolation and trusted-private-network boundaries remain unchanged.

Verify sends by counting actual synthetic turn/start calls, with multiple profiles and mixed outcomes, duplicate requests across managers, restart and preparation interruption, quota-only refresh, cancellation, and the actual browser controls. No real account login, model response or reset-cycle change is implied by those tests.

Local verification on 2026-10-07: 50 account-related tests and 39 existing Web static tests passed. The 10 batch tests cover 1–4 distinct email/workspace profiles per batch, six synthetic protocol scenarios, single/dual managers, preparation/publication interruptions and cancellation/retry. Restoring only the baseline observer method in memory made the new lock-handoff regression fail, while the current method passes. One independent change reviewer reran the two suites and reported no findings or load-bearing unknowns.

An isolated headless browser exercised the actual page and HTTP handler with four synthetic profiles: one-click start, authorization waiting, cancellation, safe continuation, page reload, explicit next round, and quota-only refresh preserving message success. Desktop 1280×900 and mobile 390×844 were observed; the mobile page had no horizontal document overflow. A corrected latency probe observed the settled mixed-result notice after 1083.6 ms cold and 1082.5 ms warm, with an unchanged no-op control (two observations, four synthetic profiles, one viewport); the one-second polling interval is part of this readout, and it is not a real-provider latency claim. An earlier probe against an intermediate notice failed its no-op control because that notice continued changing, so its timings were not used.
