# Quota applicability and observation provenance

Accepted 2026-10-22 after one independent decision review (all seven criteria accepted). The user reported that a Claude account no longer has a Claude Code subscription while Overview still showed a recent percentage and Max plan, and authorized the preceding repair recommendations.

Keep identity, subscription confirmation, observation provenance and query health separate. Record explicit user confirmation of no subscription per provider/account, never infer it from HTTP 403. Known inapplicable quotas are not current percentages or sorting inputs; preserve their original observations in details. Unexplained access refusal remains unknown. Credential plan metadata is not a current entitlement check.

The statusline producer records quota observation time separately from receipt time and carries that time with reused values. Legacy time is unknown. Readers carry provenance without requiring a new snapshot version. Remembered observations retain that provenance; a legacy timestamp cannot outrank a trustworthy observation just because an old producer refreshed it. Preserve superseded untrusted legacy values for diagnosis, without turning them into current evidence.

Use a small atomic JSON account-state file and stable lock, with one latest user confirmation per account. This operator state is independent of immutable snapshots and account memory. Ordinary collection skips confirmed unsubscribed accounts without an upstream request. Existing provider pauses stay intact. Explicit bounded recovery checks the expected account before and after the request; only this explicitly authorized path may retire a confirmation after a newer successful active query with at least one numeric window whose reset is in the future. Ordinary in-flight queries cannot create recovery receipts. Old, passive, empty or expired responses cannot do so. This proves quota query availability, not an exact paid plan tier. No new automatic retries, web mutation endpoint or subscription polling is introduced.

The operator records the confirmation on the Hub and collectors. Their copies identify the same provider/account and confirmation time; source records carry this evidence to the Hub. A newer confirmation wins over an earlier successful reading. The state remains visible across process restart and ordinary refresh. An accepted recovery retains a `restored_at` receipt beside the original confirmation; expiration of that observation later makes the quota historical, without reviving the older no-subscription claim. The Hub adopts newer confirmation/receipt metadata from admitted snapshots. User confirmation time orders the records first, so a receipt for an older confirmation cannot cancel a newer user confirmation. Recovery clears only the explicitly checked machine’s provider pause; other machines’ local confirmations and pauses require their own explicit recovery. No automatic remote unpause is implied.

Rejected alternatives: a warning alone leaves misleading numbers; deleting history loses useful evidence; classifying every 403 as no subscription invents a cause; subscription polling requires an unverified external contract and unnecessary requests; a database adds no needed capability over the existing serialized atomic-file pattern.

Preserve the original percentages/reset values (20261014-da15), whole-reading selection (20261007-a62e), failure history and explicit protected probes (20261021-6bd2, 20261022-8c27), and real-failure precedence (20261022-a6f4). Extend historical ADR-026's record with optional provenance. The old exact-field reader will reject an extended account-memory file; upgrade the reader before writers, and retain a compatible reader for rollback. Original bytes being retained does not make an old reader compatible.

Unknown: authoritative automatic subscription detection and the originating machine/time of the incident's legacy account-memory value. No fixture or local verification establishes actual provider restoration. Verification uses isolated state and synthetic upstream responses, followed by the real deployed UI using the user's subscription confirmation. Added storage has account-scale growth, no per-poll append log or TTL. State read/write failures remain visible through existing diagnostics and the synchronous operator command; this change adds no unattended operation requiring a new push alert.
