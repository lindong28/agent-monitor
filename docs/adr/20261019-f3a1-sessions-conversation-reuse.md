# Reuse unchanged conversation results across generations

Accepted 2026-10-19 after one independent decision review and a narrow identity correction. The user requested continued optimization of visible, operable Sessions while preserving functionality, accounting and freshness. Source-level reuse improved repeated opening, but a real generation update still took 2.905 seconds. This supplements [d8f4](20261019-d8f4-sessions-result-reuse.md); it does not relax statistics validation.

On a source-cache miss, read the original SQL candidates in position order and build buckets with the current complete SessionIndex. Fingerprint complete raw payloads with order and multiplicity. Reuse a previously validated and computed conversation only when its payload, statistics version, exact semantic query/window, aliases and current root metadata/status match. Bind moving windows to the existing future-event and clock-rollback guards. Unrelated session metadata changes need not invalidate other roots.

SQL identity extraction only proposes buckets. On misses, fully parse and validate every candidate and require the parsed agent/session identity to equal the SQL-proposed identity exactly. Otherwise fall back to the original whole-source reader and collector. Merely sharing a resolved root is insufficient: duplicate JSON keys may name different sessions whose ancestry later diverges. Multi-path SQL extraction returns a JSON array text, retaining escaped surrogate strings. No SQL numeric conversion or aggregation is introduced.

Run the existing Python filters, stable timestamp ordering and arithmetic on each complete changed conversation. Keep filter choices from before dimension filtering. Retain the first visible event's ordinal within each bucket, map it to this request's positions and restore original insertion order before global stable sorting. Relationship changes rebuild affected buckets; changed invalid metadata must still fail validation. A live lease is required but is never treated as proof of complete field validation.

Add a process-local LRU capped at 8192 groups and 16MiB of encoded keys/results, alongside the existing source cache. No event objects, payload bodies or leases are retained after the request; concurrent misses can compute independently. This is not an RSS bound. No persisted data, snapshot schema, importer, refresh cadence, thread or service lifecycle changes. Detail and standalone retain their existing paths. Ordinary background UI refresh retains displayed rows, as the sync-progress path already does; initial/explicit loads and errors remain visible.

Alternatives: merely skipping repeated validation or stripping metadata retained most default-window cost; TTL weakens freshness; full event caching retains substantially more data; SQL aggregation changes arithmetic; an import-generated sidecar adds persistence, cleanup and cross-process proof. Archive corrections and renumbered positions rule out assuming append-only input. The isolated scan/hash lower bound was 0.382 seconds for the fixed 30-day candidate corpus and 1.522 seconds for all history; these exclude SessionIndex construction, cache operations and response encoding and are not end-to-end gains.

First process-cold reads still decode all candidates and may incur additional grouping cost. New-generation work still scans candidate bytes, and a large changed conversation still requires full decoding. Measure actual cold/update behavior, complete response equivalence, invalidation, malformed and duplicate-key inputs, ordering and bounded retention before delivery. Production unknown inputs have no guaranteed automatic semantic-error detection time. Rollback is compatible source deployment and process replacement, with no migration. The execution record and diagnostic decision packet/review preserve evidence and remaining acceptance work.
