# Service diagnostics

A Monitor-owned account can publish its first explicit quota observation even when it is absent from the portable `codex-account` collector registry. Its local `codex-accounts/<UUID>/profile.json`, workspace and email establish that source; cache writes, owning-machine publication and quota-view merging verify this identity. This does not copy credentials, create a collector registration or enroll the account in automatic queries. Native and remote source admission retain their existing contracts. See [local quota commit](../adr/20261107-7c21-local-quota-commit.md).

Later ordinary explicit refreshes use the same local cache in the normal quota view, after the registered profile's retained observation and cache timestamp agree. A recovery candidate still uses the transactional publication path until committed. If the local cache becomes unreadable, existing published observations remain available with a cache-error notice; an observation timestamp is not advanced by that fallback.

Local Monitor additions also require the current physical host identity to match the admitted machine generation. A publication from another host identity or machine endpoint does not authorize local-cache substitution. Failure to verify the physical identity is a local prerequisite failure, not a reason to change egress or issue another provider request.

If official authorization and quota verification succeed but local saving fails, the recovery card offers **保存已有配额结果** while the retained candidate and its current window remain valid. This only resumes local saving/publication and the original quota task; it does not authenticate, preview egress, query quota or send messages. Changed identity, operation, pause, restrictions or an expired candidate refuse the action. A failed local retry retains the candidate and pause and releases only its own local attempt. Recovery clients capture available route-bridge connection facts before shutdown; earlier missing facts and the human authorization browser's route remain unverified, without replaying upstream work to fill the gap.

Recovery-state reads also verify the owning host identity. On macOS this uses `/usr/sbin/ioreg` directly, so a managed service does not depend on an interactive shell's PATH. A failed recovery-state read retains the pause and records safe exception facts in the existing diagnostics sink; it never queries the provider. Check the actual account page as well as process health after deployment.

Installation, update and existing-installation transition are documented in [usage and operations](../public-usage.md). Run lifecycle commands from the owning checkout. `./agent-monitor service status` includes both the central target and the optional local dashboard; `/api/health?asset_watch=1` identifies the responding Web instance. Source preflight alone does not prove service health. Inspect `state/server.log` for local startup failures and `state/rollup-daemon.log` for collection failures. A previous nonzero collector exit is historical; confirm the latest result before attributing a current outage. Never remove persistent locks or replace an existing state symlink to force startup.

Managed deployment checks the Hub's `/api/health?asset_watch=1` and the connector's loopback `/health`. Their `source_root` and `deployment_signature` identify the checkout and source/selected configuration captured at process startup; changing a plist alone is not proof of activation. The installer checks this identity with a bounded wait after replacement and retains an already matching process. This proves local process response, not browser access, collected-data admission, provider availability or completion of account actions. Hub startup diagnostics remain in `state/hub.log`; connector connection/failure observations remain at its configured status-file path. Deployment failures are synchronous nonzero installer results; no new background alert service is installed.

Ordinary Web, Hub and collector log retention is configured in [ordinary service logs](../public-usage.md#ordinary-service-logs). The capacity is checked at existing service boundaries, with possible temporary overshoot and concurrent-write loss during truncation. It does not govern diagnostic events or accounting history. Rotation success is not service-health evidence.

## Network diagnostic findings

The `/network` page and `agent-monitor network` report describe the server machine's latest diagnostic observation, not a historical range, the browser device's IP or provider-account availability. A `range=30d` URL parameter does not change this page's data. Read the observation timestamp, cache receipt and missing-observation messages before acting on a risk label.

IPv4 and IPv6 addresses are source addresses selected by the OS route to the probe's fixed targets, not an enumeration of all interfaces or a public IPv6 leakage test. DNS country labels come from a static service list, not resolver geolocation. The two [Tailscale DNS addresses](https://tailscale.com/docs/reference/quad100) identify a local DNS proxy; its upstream remains unverified. Private addresses alone do not identify a router. The configured list does not establish the resolver actually used for each target, including split DNS.

Proxy and hosting flags come from ip-api; a negative flag does not prove requests use no proxy. Reputation lookups run only when those flags trigger escalation. The page distinguishes an intentionally skipped lookup from a failed or incomplete lookup. The proxycheck risk score uses the existing 30/70 thresholds; its separate provider text remains visible even when its classification differs from ip-api. Stopforumspam's separate [confidence percentage](https://stopforumspam.com/usage) estimates unwanted activity from its records; it is not proxycheck risk or an account-ban probability, and an unlisted IP has no fabricated zero score. Its `frequency=255` can be a blacklist placeholder with a changing `lastseen`, so those values are labeled as provider fields rather than verified report counts and dates. Timezone comparison uses reported names when available, otherwise current UTC offsets; different names can have the same offset. A mismatch alone establishes neither an outage nor a need to change the host timezone. Existing local risk rules remain unchanged and do not guarantee account availability.

If the report names an unresponsive proxy, first check the selected system proxy and whether that proxy process is running on the report's machine. Keep the installation's established route; do not switch machines, proxies or direct access merely to make a diagnostic succeed. For partial public-IP, DNS or reputation results, inspect the named section's error and retain the unknown result instead of treating it as a clean reading. Review the intended region and local timezone before changing either setting.

After an authorized correction, use **重新检测** or run `agent-monitor network --force` on the same machine and compare the affected observation and timestamp. Both respect the shared 60-second cache and any longer upstream `Retry-After` delay; a click can reuse the previous result. The page reports whether this read probed or reused a result and the earliest next probe time. Refresh can contact external services after the cache expires; do not run it as an offline check. Use `agent-monitor network --json` when retaining a structured report, and remove private addresses or metadata before sharing it. Quota holds use the separate [recovery procedure](#paused-codex-quota-queries); a network risk label does not authorize clearing a hold or replaying an account action.

## Automatic quota region skips

`query_state=skipped` with `refresh_skip` means automatic egress admission stopped this machine's batch: `china`, `unknown` or `route_changed`. Inspect the collection details for the reason and check time; the retained quota observation time does not advance. These outcomes do not create provider/account pauses and do not exclude the same account on another machine. No automatic retry is added: the next normal quota interval checks again. Existing pauses still take precedence and do not cause a probe just to discover that querying is already forbidden. The collector's “Quota cycle processed” log describes completion of scheduling, not proof of a provider request or fresh quota.

The protected scope covers model-company requests from automatic quota readers; anonymous region probes, local accounting, GitHub pricing and machine synchronization remain separate. Keep the installation's shared model-domain proxy rules; do not switch exits to investigate a skip. See [the public behavior and limitations](../public-usage.md#optional-quota-and-account-actions). Use `python -m unittest discover -s tests -p 'test_automatic_egress.py'` for isolated CN/unknown/non-CN child-transport counters and `node --test tests/test_system_proxy.cjs` for route changes, expiry and fallback. These are synthetic checks, not evidence of live provider availability.

Review the recipient before sharing it. A failed status read marks retained details as historical.

**通过目标机器路由桥检查配额** opens the shared egress preview and requires a one-time confirmation bound to that machine, complete account identity and pause ID. It performs one `account/rateLimits/read`, without a model turn or automatic retry. It clears the pause only after saving a current quota window to that machine's quota cache. Identity changes, invalid windows and save failures keep the pause. A lost response is an unknown outcome; reread local state before another action. A failed probe may create a new pause ID, but never authorizes another probe automatically. **核对后解除此账号限制** only clears the individual restriction, not the shared pause. The shared hold is local protection, not evidence that all accounts have failed upstream.

For a bound Monitor profile whose current quota failure is HTTP 401/token_revoked, the card instead recommends **刷新认证并检查配额**. This is a distinct operation: its `mode=renew_auth` request, `quota-auth-recovery` confirmation and mode-bearing scope cannot reuse quota-only approval. It uses the same owning-machine route, profile lock, pause lease and cumulative child deadline. After local credential preflight, it requests official managed authentication refresh once; only a changed access token with the same account identity permits one quota read. An account response alone does not establish refresh success, and a routing RPC failure can follow a persisted credential change. No new credential, changed identity, transport failure or deadline exhaustion stops the operation. Codex can perform internal routing/prewarming and additional HTTP/OAuth operations; the explicit RPC bounds do not count those as one network request. Authentication repair and its safe phase results remain in the existing recovery receipt after reload. Valid saved quota is required before clearing the pause. Old account-operation failures remain available as history; the recovered quota task displays its new observation. See [the decision](../adr/20261106-7c21-explicit-auth-recovery.md).

After recovery, **返回发送操作** reloads account state and returns focus to continuing known-unsent accounts or starting a new round. It does not send anything. Account selections and previous results remain; login and individual restrictions still apply. **查看最近恢复记录** remains available after the pause disappears and after reload. A recovery card for another machine does not offer continuation of the local account batch. **首次启用、连接与授权帮助** contains the optional sending-egress preview; its result does not establish the quota-recovery egress.

Obtain the values from the dashboard and the local `state/upstream_controls/codex.json`; run only after approving that specific probe. Never delete the files to force a retry.

Normal refresh and manual recovery use account-bound quota readers on the account-owning machine. The all-account quota action excludes accounts that need login or have an authentication, unknown-outcome, rate-limit or login-rate-limit restriction. The overview uses the managed-card selection: select all to cover the whole available set, or select individual cards. The query button counts only selected queryable accounts. It confirms that exact current queryable set once, then queues one quota-only operation per account serially; it never sends a model turn. If that set changes before submission, the server requires a fresh confirmation. Use the dashboard recovery endpoint or the installed `quota-recover` command on that machine; do not replace this chain with a direct SDK/curl call, a personal CLI proxy, another host or a different proxy node. The browser's route to this internal dashboard does not determine the backend's upstream route; the recovery card names the owning machine and the confirmation dialog states that both the egress preview and the check use that machine's Agent Monitor route bridge. When the dashboard runs on a Hub, it obtains the preview by invoking the installed `quota-recover --egress-preview` on the owning machine over the configured machine link; it does not use the Hub's own egress as a substitute. Query approval does not include changing egress; if the existing route or a project regional/fixed-IP requirement cannot be verified, retain the pause and inspect local configuration and existing evidence first.

Recovery CLI and HTTP receipts include `network` from the same local proxy bridge, scoped to this operation. `policy` identifies the resolver; `events` report target origins, selected proxy routes, connection results, times and configuration generations. `coverage: recent_connections_only` means the bridge's bounded recent connection history, not full request accounting or proof of a final public IP/country. `coverage: unavailable` means evidence could not be obtained; empty events do not prove no upstream request occurred. These observations do not alter `ok`, clear a pause, authorize a retry or trigger a separate public IP probe. The owning machine stores one latest recovery receipt, with at most 64 connection events, in the existing locked `state/upstream_controls/codex.json`; quota snapshots are unchanged. The stored receipt binds the original pause/account to the resulting pause and can be read after a reload or lost HTTP response. A late result cannot overwrite an unrelated pause; storage failures are explicit in the immediate receipt. Old receipts without saved diagnostics do not contain those details; other retained logs or backups must be checked before concluding whether historical evidence can be recovered. Proxy credentials and request paths/bodies are not included.

The diagnostic panel separates Monitor HTTP, Codex RPC and upstream HTTP codes. For example, Monitor HTTP 409 wraps an unsuccessful recovery; it does not establish that the provider returned 409. RPC -32603 alone does not distinguish authentication, transport or other internal failures. An upstream 401/token_revoked classification is retained as an upstream response, not presented as proof that credentials are unusable; if the target-machine check still fails, the page hands the account, deployment and diagnostic follow-up to an Agent Monitor maintainer. A failed recovery is matched against its requested pause or the resulting pause, with the machine, account and managed profile identity retained; a new pause ID from that failure does not make it an unchecked incident. Bridge `connected` observations establish a bridge connection, not successful quota retrieval or the final public egress IP/region. After any probe response, the panel rereads local state without retrying the provider; historical diagnostics remain separate from that current state.

If the explicit authentication refresh returns no changed credentials, the card states that quota was not queried and keeps the pause. It hides an ordinary retry with those unchanged credentials. The existing receipt can include a redacted client stderr excerpt, limited to 512 characters from a bounded 64 KiB input; it is diagnostic context, not a provider error classification. Older receipts may lack it. Do not infer permanent credential failure, automatically restart login or clear the pause from this outcome.

For a matching managed account on the Hub itself, **重新授权并复验配额** offers an explicitly confirmed official device-authorization operation on that owner's route. It binds the current pause and original unsent quota task. The account card shows the official device URL/code and existing cancel control. The person must authorize the selected email and workspace. Device confirmation waits at most ten minutes, with separately bounded client and validation phases; this occupies the same-machine Codex lane. No message is sent. A failed or unknown completion may have saved credentials: preserve them and inspect the result instead of requesting another code automatically. Only same-identity new credentials, one valid quota read, saved account/cache results and matching pause/probe permit completion. Success restores the original quota task and retains its first failure and preceding recovery record. Ordinary login remains subject to its existing pause boundary; do not use it to bypass this confirmation. Non-Hub source nodes do not advertise this asynchronous recovery option.

Account-action quota queries retain these same safe RPC/upstream facts in the operation, its saved failure and any resulting shared pause. **配额查询失败** identifies an unsuccessful query; **配额查询未执行** identifies a local admission refusal. The account card keeps the earlier sending restriction and dated successful quota observation separate from this latest attempt. While the shared channel is paused, follow **查看通道暂停与检查** rather than the disabled refresh button. Old operation records that saved only an RPC code lack an upstream summary in that record; other retained sources are not ruled out. Opening the page does not retry them.

For a recovery tied to a Monitor account's quota-only operation, the saved result also applies the account's normal permission rule. A matching Codex bucket with `ordinaryUsageAllowed=true` removes only the quota sending hold, provided neither `spendControlReached=true` nor a `rateLimitReachedType` denies usage. False or missing permission retains that hold even when the query succeeds, percentages are zero or the reset has passed. Authentication, unknown-outcome and rate-limit holds are unchanged. Query success and permission to send are separate outcomes; no recovery starts a message automatically. The child-reader `RateLimits` contract carries these optional permission fields; passive/legacy readings default to unknown. The account response additionally supplies keyed `restriction_messages` for presentation while retaining the older `restriction_details` list for existing consumers.

Combined refresh rounds suppress later calls for the same provider/account fingerprint after a failure; confirmed independent accounts/providers may continue. Missing identity suppresses that provider for the rest of the round. SSH failure or an unusable reply cannot prove the upstream call did not happen, so both providers are suppressed when the execution scope is unknown. Exclusions are checked against the account at the actual reader, including the GUI collector. Restricted GUI requests use separate v2 request/receipt files so an older collector cannot silently ignore them. This is protection within one combined round, not a distributed pause across independent schedulers.

New RPC diagnostics retain protocol codes plus an upstream error summary, not full response bodies. The summary removes credential headers, bearer values, URL userinfo and recognized credential parameters, normalizes whitespace and retains at most 512 characters. Ordinary URLs, query context and long correlation identifiers are preserved for diagnosis in the private/trusted-reader deployment; neither an HTTPS address nor a long string alone establishes a secret. This is not a general-purpose secret detector or a public-sharing projection. The dashboard has no client authentication: keep its state, cache, snapshots, proxies and backups within the intended readers' access boundary, and reassess the diagnostic output before changing that boundary.

The UI calls this an error summary rather than an original response. `[url redacted]` and `[opaque value redacted]` are processing placeholders: information represented by them cannot be reconstructed from the saved summary, but the placeholder alone does not establish that the address or identifier was risky or which rule version produced it. New failures use the current retention rules, but viewing or copying diagnostics never retries a provider request to replace missing evidence. **复制诊断信息** includes the displayed summary, processing/loss explanation and account, machine, path and address context for an authorized maintainer. It is not suitable for direct public posting; inspect the content and recipient before sharing. The existing diagnostics view plus the synchronous recovery receipt expose failures; this change does not install a separate notification service.

## Account-local quota failures

The account dashboard keeps quota batches separate from message batches. **刷新可查询账号配额**, **查询所选账号配额** and **继续未完成的账号配额查询** use the existing route bridge and one-time approval bound to the exact account subset and quota-batch revision. Continuation preserves successful observations and excludes disabled accounts and login/authentication/unknown/rate-limit holds; a quota-only sending restriction remains queryable. A newer batch or eligibility change requires a new preview. Restart retains the latest batch and its per-account outcomes but never starts requests automatically.

Explicit quota credential refusals include both `token_expired` and `token_revoked`. These are reported upstream codes, not independent proof of actual expiration or revocation. Automatic account isolation additionally requires the exact Codex quota transport envelope and an unchanged account identity and credential generation. A managed account's **刷新认证并检查配额** action reuses official refresh; normal queries do not refresh or retry automatically. A verified refusal of the refreshed credential retains account-only protection; unknown failures retain shared protection.

For a historical `operationFailed` shared pause tied to a failed, unsent quota query with a recorded 401 credential refusal, **确认仅此账号异常，解除本次通道暂停** allows explicit operator attribution without disabling the account. Confirm only after checking the displayed original account and operation. The action first saves account protection, retains the original failure and attribution, then clears only the matching shared pause; it sends no provider request and does not claim authentication recovery or invent historical credential evidence. Existing account protection, an active operation, conflicting source or identity prevents attribution. Open that account's login repair separately; use **批量操作 → 继续未完成的 N 个账号配额查询** to confirm the independent eligible subset. Completed accounts retain their previous readings and are not replayed. See [the decision and evidence boundary](../adr/20261110-c3a5-quota-credential-refusals.md).

Use **详情与维护 → 账号维护 → 停用此账号** for an account the operator knows is unavailable. This is a local Monitor decision, not an automatically diagnosed provider ban. It preserves credentials, identities and history, and blocks this identity in both account actions and the owning machine's native/discovered quota reader and recovery. Other machines retain their own local state. **重新启用此账号** removes only that operator disable; other restrictions and provider pauses remain. No provider request is made by either action.

Explicit account-scoped protocol authentication failures are isolated; status-only HTTP 401/403, unknown errors and shared route failures do not establish account scope. New operation pauses retain their account and operation source, and recovery resolves that exact Monitor profile instead of falling back to native credentials. Existing account authentication holds no longer become provider pauses merely because another operation starts. Unknown sends and shared/login rate-limit protection remain.

For a current `operationFailed` pause caused by an actually attempted quota-only failure, an already disabled account can expose **确认仅此账号异常，解除本次通道暂停**. This explicit operator attribution checks the current pause and operation, rejects active work, conflicting sources, used probes, shared-route/rate-limit evidence and unknown sends, and retains the original pause plus attribution receipt. It neither proves network recovery nor clears other account holds. Legacy unbound pauses require this explicit attribution; they are never automatically mapped by timestamp. Old queries without batch IDs remain individual history: select only the still-unqueried accounts to start a new confirmed subset, rather than fabricating an old batch or repeating successful queries.

State remains in the existing owning machine's `state/codex-accounts`: one latest `quota-batch.json` and one retained quota-batch result per profile. Operator disable and prior failures stay in profile metadata; shared pauses and the latest attribution receipt stay in `state/upstream_controls/codex.json`. Writes preserve existing locks and identities; no new retention sweep, account database or background alert service is introduced. The account cards, batch summary and recovery diagnostics are the synchronous failure surfaces. See [the decision and acceptance boundaries](../adr/20261104-account-quota-isolation.md).

## Runtime performance diagnostics

`GET /api/diagnostics` reports the serving process's active operations, recent completions, cumulative counts, coverage and source freshness. Read it at the actual address printed by `./agent-monitor status`; it does not acquire the query-view or sync lock. The observer also writes `state/diagnostics/current.json` and bounded `events.jsonl` files. Inspect these locally when HTTP is unresponsive, and sanitize paths/account data before sharing any logs.

```bash
python3 -m json.tool state/diagnostics/current.json
```

Keep `instance_id`, `sampled_at` and observer/persistence status with a reading. Restart resets counters and changes the instance. Recent samples are bounded, not a latency distribution or complete attempt ledger. `coverage` reports omitted active details, evicted completed samples and dropped events; event emission is not an fsync guarantee. A stale `current.json` does not establish that the observer is still running.

Read `active.phase` to distinguish JSON encoding, response-body writing and publication. HTTP durations include encoding and body writing, but not header parsing. Nested operations overlap; summing their durations double-counts elapsed time. A generic running phase does not prove lock contention. The reported slow/long-running thresholds are observation thresholds, not cancellation deadlines.

For a slow dashboard, measure at the URL selected by `agent-monitor open`; central mode may cross a network even when invoked locally. Browser Navigation/Resource Timing separates document loading, asset validation, API first byte and response-body receipt. Compare each API resource's `Server-Timing: app` with its full browser duration; the server finishing a write does not prove the browser has received or rendered it. Measure the first versioned load and subsequent navigations/reloads separately. Warm versioned assets can show zero transferred bytes; hard reload or cache-disabled developer tools intentionally bypass reuse. Check rendered data as well as timing, and distinguish a readable existing snapshot from completion of a background collection round. Network variation means a handful of timings are observations, not a latency guarantee.

After changing static files or deploying, the HTML and dynamic modules must select the new Web version; an already-open page uses the existing health watcher to offer an explicit refresh instead of forcing navigation. The refresh preserves the current viewport, expanded details and focus when the page can restore them. `tests/test_http_delivery.py` covers version changes, vendor symlinks, conditional GET, HEAD and lossless compression on an isolated HTTP socket. These tests establish protocol behavior, not latency on an operator's network.

For synchronization progress, read `/api/sync-status` and the affected source's collector/export logs. `observed_age_seconds` concerns collection observation; `generated_age_seconds` concerns publication. `age_intervals` is observation age divided by configured interval, not a count of missed rounds. Missing metadata stays unknown. A cleared incident means a later sample no longer saw that condition, not that every operation is healthy.

Statistics refresh, network refresh and restart use POST with same-origin checks and `X-Agent-Monitor: action`. Legacy GET/HEAD force parameters do not trigger these explicit actions. Normal quota/collection schedules are separate. Let active account operations finish before restart; do not replay an uncertain send. See [account operations](../public-usage.md#optional-quota-and-account-actions).

## Isolated backend investigation

From a development checkout with its dependencies installed, run:

```bash
.venv/bin/python scripts/benchmark_backend.py --rows 100 1000 --padding-mib 0 4 --repeat 3
```

The script creates synthetic snapshots in its own temporary HOME/state and calls real admission, QueryView and aggregate code. It does not start HTTP, SSH or providers. Cases run serially because disk/cache contention would contaminate comparisons. JSON stdout contains raw samples; save it outside temporary directories if retaining evidence. Exit zero means measurement completed, not an SLA pass.

Rows and padding vary aggregate cardinality and snapshot bytes separately. Compare application-cold admission, hot admission, preparation, prepared reads and generation changes; application-cold does not flush the OS cache. Padding does not model real session retention or network traffic. Use the [cost map](../public-architecture.md#backend-performance-checks) to select the affected consumer and its existing regressions. Real page/API latency requires measurements at that consumer, separately from these synthetic results.

### Background collection and export

```bash
.venv/bin/python scripts/benchmark_backend.py background --rows 100 1000 --repeat 2
.venv/bin/python scripts/benchmark_backend.py background --rows 1000 10000 --repeat 3 --json > background.json
.venv/bin/python scripts/benchmark_backend.py background --pipeline rollup --rows 1000 10000 --repeat 3 --json > rollup-background.json
```

The background mode generates Codex token events, calls the real archive/collector, then rollup and validated export with the collected entries. Each round loads once and feeds that result to export; it does not replay independently scheduled collect and requested export processes. Each case runs in a fresh child with isolated HOME and state. It measures initial collection, repeated unchanged input and one appended event per changed round. A deterministic synthetic price table exercises the real local cost calculation; price-provider calls are replaced, quota calls are prohibited, socket connections are blocked and only the fixture's local Git identity lookup is allowed as a child process. Exporter clean-tree identity checking is replaced with a synthetic manifest identity so a dirty optimization candidate can be measured; the report records actual source hashes separately. This does not exercise the production exporter identity gate.

The default table shows full-round CPU/wall time and parsed-file counts. `--pipeline rollup` measures the scheduled bucket path without full event export. `--json` retains non-overlapping collection and export/rollup phases, source hashes (including dirty content), environment, accounting checks, archive/result database bytes and worker peak RSS. It also counts decoded archive entries and priced entries; compare work counts as well as timing to distinguish incremental work from a faster full scan. CPU includes reaped children; peak RSS includes setup/readback, excludes children and is not incremental phase memory. Setup, fixture mutation, extra verification and cleanup are outside the timed operation. Export samples verify snapshot event/input/output token totals, zero cache counters and nominal event costs; both modes verify rollup input/output tokens, entry/known-cost counts and known cost totals. Failures exit nonzero. The parent cleans temporary state on the default 120-second per-case timeout; completed cases remain in a failed JSON report. Use `--timeout` to set a different explicit bound.

These synthetic cases expose retained-history growth and input invalidation; they do not represent real log distributions, startup imports, price/quota providers, transport, schedules, idle wakeups or production heat/power. Unchanged input may avoid parsing while still materializing and exporting all history. Compare the same rows/repeats, source hashes and environment before/after; a faster export phase alone does not establish lower total background cost. Tests for the instrument live in `tests/test_benchmark_background.py`. Retain JSON outside temporary directories when using it as evidence; inputs are regenerated by the versioned script.
