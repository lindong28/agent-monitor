# Service diagnostics

Installation, update and existing-installation transition are documented in [usage and operations](../public-usage.md). Run lifecycle commands from the owning checkout. `./agent-monitor service status` includes both the central target and the optional local dashboard; `/api/health?asset_watch=1` identifies the responding Web instance. Source preflight alone does not prove service health. Inspect `state/server.log` for local startup failures and `state/rollup-daemon.log` for collection failures. A previous nonzero collector exit is historical; confirm the latest result before attributing a current outage. Never remove persistent locks or replace an existing state symlink to force startup.

Managed deployment checks the Hub's `/api/health?asset_watch=1` and the connector's loopback `/health`. Their `source_root` and `deployment_signature` identify the checkout and source/selected configuration captured at process startup; changing a plist alone is not proof of activation. The installer checks this identity with a bounded wait after replacement and retains an already matching process. This proves local process response, not browser access, collected-data admission, provider availability or completion of account actions. Hub startup diagnostics remain in `state/hub.log`; connector connection/failure observations remain at its configured status-file path. Deployment failures are synchronous nonzero installer results; no new background alert service is installed.

Ordinary Web, Hub and collector log retention is configured in [ordinary service logs](../public-usage.md#ordinary-service-logs). The capacity is checked at existing service boundaries, with possible temporary overshoot and concurrent-write loss during truncation. It does not govern diagnostic events or accounting history. Rotation success is not service-health evidence.

## Network diagnostic findings

The `agent-monitor network` report describes the server machine's observed route, not the browser device's IP or provider-account availability. Read the timestamp and missing-observation messages before acting on a risk label. A local IPv6 address is not proof of public IPv6 leakage; DNS resolver and IP-reputation observations do not establish whether an account can use a provider.

If the report names an unresponsive proxy, first check the selected system proxy and whether that proxy process is running on the report's machine. Keep the installation's established route; do not switch machines, proxies or direct access merely to make a diagnostic succeed. For partial public-IP, DNS or reputation results, inspect the named section's error and retain the unknown result instead of treating it as a clean reading. Review the intended region and local timezone before changing either setting.

After an authorized correction, run `agent-monitor network --force` on the same machine and compare the affected observation and timestamp. This requests fresh public diagnostics and can contact external services; do not run it as an offline check. Use `agent-monitor network --json` when retaining a structured report, and remove private addresses or metadata before sharing it. Quota holds use the separate [recovery procedure](#paused-codex-quota-queries); a network risk label does not authorize clearing a hold or replaying an account action.

## Paused Codex quota queries

Quota observation age and active-query health are independent. A recent Codex session log can supply a fresh reading while the machine's active query remains paused. Expand the reading timestamp for its source, and expand **Codex 采集详情** for the affected machine, account, pause time and available failure evidence. Legacy pauses without an upstream reason remain unknown; fresh session activity or a restart does not clear them.

The account panel automatically opens a recovery card beside disabled send controls. Its current state and one recommended action stay visible; **技术详情与复制诊断** keeps workspace identifiers, credential paths, raw diagnostic summaries and connection observations secondary. **更新状态** (or **重新读取状态** when the outcome is unknown) uses `GET /api/quota-recovery?machine=...` and the owning machine's `agent-monitor quota-recover --status`: neither queries the provider nor clears a pause. Quota failure details provide **查看当前状态与恢复** for their specific machine and share the same card. Local identity records are not proof of upstream authentication.

The recovery card distinguishes an available check, a failed check, an active operation, an already-used check, unreadable pause state and incomplete identity. Failed checks recommend **查看排查步骤** first, with **处理后再次检查配额** available when permitted. An unknown outcome recommends rereading the existing result before another attempt. The main card identifies the machine and account, and keeps the last check separate from the current pause state. **复制诊断信息** copies already-read information without another request; a selectable text box is available when the Clipboard API is unavailable. Review the recipient before sharing it. A failed status read marks retained details as historical.

**检查配额并尝试恢复** asks for confirmation for that machine, complete account identity and pause ID. It performs one `account/rateLimits/read`, without a model turn or automatic retry. It clears the pause only after saving a current quota window to that machine's quota cache. Identity changes, invalid windows and save failures keep the pause. A lost response is an unknown outcome; reread local state before another action. A failed probe may create a new pause ID, but never authorizes another probe automatically. **核对后解除此账号限制** only clears the individual restriction, not the shared pause. The shared hold is local protection, not evidence that all accounts have failed upstream.

After recovery, **返回发送操作** reloads account state and returns focus to continuing known-unsent accounts or starting a new round. It does not send anything. Account selections and previous results remain; login and individual restrictions still apply. **查看最近恢复记录** remains available after the pause disappears and after reload. A recovery card for another machine does not offer continuation of the local account batch. **发送方式与连接帮助** contains the optional sending-egress preview; its result does not establish the quota-recovery egress.

The equivalent operator command on the owning machine is `agent-monitor quota-recover --request '{"machine":"YOUR_MACHINE","account_id":"CURRENT_ACCOUNT_ID","account_label":"CURRENT_ACCOUNT_LABEL","pause_id":"CURRENT_PAUSE_ID"}'`. Obtain the values from the dashboard and the local `state/upstream_controls/codex.json`; run only after approving that specific probe. The JSON receipt reports `ok`, with safe failure facts when available. Provider pauses and their last record remain bounded local files, protected by the existing persistent locks. Never delete the files to force a retry.

Both normal refresh and manual recovery call `agent_monitor.quota.quota_refresh.load_rate_limits` on the account-owning machine. The reader and its Codex child consume `agent_monitor.network.network_policy.child_environment`, which uses the product's Chromium system-proxy resolver independently of shell proxy variables and isolated account HOME. Use the dashboard recovery endpoint or the installed `quota-recover` command on that machine; do not replace this chain with a direct SDK/curl call, a personal CLI proxy, another host or a different proxy node. The browser's route to this internal dashboard does not determine the backend's upstream route. Query approval does not include changing egress; if the existing route or a project regional/fixed-IP requirement cannot be verified, retain the pause and inspect local configuration and existing evidence first.

Recovery CLI and HTTP receipts include `network` from the same local proxy bridge, scoped to this operation. `policy` identifies the resolver; `events` report target origins, selected proxy routes, connection results, times and configuration generations. `coverage: recent_connections_only` means the bridge's bounded recent connection history, not full request accounting or proof of a final public IP/country. `coverage: unavailable` means evidence could not be obtained; empty events do not prove no upstream request occurred. These observations do not alter `ok`, clear a pause, authorize a retry or trigger a separate public IP probe. The owning machine stores one latest recovery receipt, with at most 64 connection events, in the existing locked `state/upstream_controls/codex.json`; quota snapshots are unchanged. The stored receipt binds the original pause/account to the resulting pause and can be read after a reload or lost HTTP response. A late result cannot overwrite an unrelated pause; storage failures are explicit in the immediate receipt. Old attempts without saved diagnostics cannot be reconstructed. Proxy credentials and request paths/bodies are not included.

The diagnostic panel separates Monitor HTTP, Codex RPC and upstream HTTP codes. For example, Monitor HTTP 409 wraps an unsuccessful recovery; it does not establish that the provider returned 409. RPC -32603 alone does not distinguish authentication, transport or other internal failures. Bridge `connected` observations establish a bridge connection, not successful quota retrieval or the final public egress IP/region. After any probe response, the panel rereads local state without retrying the provider; historical diagnostics remain separate from that current state.

Combined refresh rounds suppress later calls for the same provider/account fingerprint after a failure; confirmed independent accounts/providers may continue. Missing identity suppresses that provider for the rest of the round. SSH failure or an unusable reply cannot prove the upstream call did not happen, so both providers are suppressed when the execution scope is unknown. Exclusions are checked against the account at the actual reader, including the GUI collector. Restricted GUI requests use separate v2 request/receipt files so an older collector cannot silently ignore them. This is protection within one combined round, not a distributed pause across independent schedulers.

New RPC diagnostics retain protocol codes plus an upstream error summary, not full response bodies. The summary removes credential headers, bearer values, URL userinfo and recognized credential parameters, normalizes whitespace and retains at most 512 characters. Ordinary URLs, query context and long correlation identifiers are preserved for diagnosis in the private/trusted-reader deployment; neither an HTTPS address nor a long string alone establishes a secret. This is not a general-purpose secret detector or a public-sharing projection. The dashboard has no client authentication: keep its state, cache, snapshots, proxies and backups within the intended readers' access boundary, and reassess the diagnostic output before changing that boundary.

The UI calls this an error summary rather than an original response. `[url redacted]` and `[opaque value redacted]` are processing placeholders: information represented by them cannot be reconstructed from the saved summary, but the placeholder alone does not establish that the address or identifier was risky or which rule version produced it. New failures use the current retention rules, but viewing or copying diagnostics never retries a provider request to replace missing evidence. **复制诊断信息** includes the displayed summary, processing/loss explanation and account, machine, path and address context for an authorized maintainer. It is not suitable for direct public posting; inspect the content and recipient before sharing. The existing diagnostics view plus the synchronous recovery receipt expose failures; this change does not install a separate notification service.

## Runtime performance diagnostics

`GET /api/diagnostics` reports the serving process's active operations, recent completions, cumulative counts, coverage and source freshness. Read it at the actual address printed by `./agent-monitor status`; it does not acquire the query-view or sync lock. The observer also writes `state/diagnostics/current.json` and bounded `events.jsonl` files. Inspect these locally when HTTP is unresponsive, and sanitize paths/account data before sharing any logs.

```bash
python3 -m json.tool state/diagnostics/current.json
```

Keep `instance_id`, `sampled_at` and observer/persistence status with a reading. Restart resets counters and changes the instance. Recent samples are bounded, not a latency distribution or complete attempt ledger. `coverage` reports omitted active details, evicted completed samples and dropped events; event emission is not an fsync guarantee. A stale `current.json` does not establish that the observer is still running.

Read `active.phase` to distinguish JSON encoding, response-body writing and publication. HTTP durations include encoding and body writing, but not header parsing. Nested operations overlap; summing their durations double-counts elapsed time. A generic running phase does not prove lock contention. The reported slow/long-running thresholds are observation thresholds, not cancellation deadlines.

For a slow dashboard, measure at the URL selected by `agent-monitor open`; central mode may cross a network even when invoked locally. Browser Navigation/Resource Timing separates document loading, asset validation, API first byte and response-body receipt. Compare each API resource's `Server-Timing: app` with its full browser duration; the server finishing a write does not prove the browser has received or rendered it. Measure the first versioned load and subsequent navigations/reloads separately. Warm versioned assets can show zero transferred bytes; hard reload or cache-disabled developer tools intentionally bypass reuse. Check rendered data as well as timing, and distinguish a readable existing snapshot from completion of a background collection round. Network variation means a handful of timings are observations, not a latency guarantee.

After changing static files or deploying, the HTML and dynamic modules must select the new Web version; an already-open page uses the existing health watcher to reload. `tests/test_http_delivery.py` covers version changes, vendor symlinks, conditional GET, HEAD and lossless compression on an isolated HTTP socket. These tests establish protocol behavior, not latency on an operator's network.

For synchronization progress, read `/api/sync-status` and the affected source's collector/export logs. `observed_age_seconds` concerns collection observation; `generated_age_seconds` concerns publication. `age_intervals` is observation age divided by configured interval, not a count of missed rounds. Missing metadata stays unknown. A cleared incident means a later sample no longer saw that condition, not that every operation is healthy.

Statistics refresh, network refresh and restart use POST with same-origin checks and `X-Agent-Monitor: action`. Legacy GET/HEAD force parameters do not trigger these explicit actions. Normal quota/collection schedules are separate. Let active account operations finish before restart; do not replay an uncertain send. See [account operations](../public-usage.md#optional-quota-and-account-actions).

## Isolated backend investigation

From a development checkout with its dependencies installed, run:

```bash
.venv/bin/python scripts/benchmark_backend.py --rows 100 1000 --padding-mib 0 4 --repeat 3
```

The script creates synthetic snapshots in its own temporary HOME/state and calls real admission, QueryView and aggregate code. It does not start HTTP, SSH or providers. Cases run serially because disk/cache contention would contaminate comparisons. JSON stdout contains raw samples; save it outside temporary directories if retaining evidence. Exit zero means measurement completed, not an SLA pass.

Rows and padding vary aggregate cardinality and snapshot bytes separately. Compare application-cold admission, hot admission, preparation, prepared reads and generation changes; application-cold does not flush the OS cache. Padding does not model real session retention or network traffic. Use the [cost map](../public-architecture.md#backend-performance-checks) to select the affected consumer and its existing regressions. Real page/API latency requires measurements at that consumer, separately from these synthetic results.

### Background collection and export

```bash
.venv/bin/python scripts/benchmark_backend.py background --rows 100 1000 --repeat 2
.venv/bin/python scripts/benchmark_backend.py background --rows 1000 10000 --repeat 3 --json > background.json
.venv/bin/python scripts/benchmark_backend.py background --pipeline rollup --rows 1000 10000 --repeat 3 --json > rollup-background.json
```

The background mode generates Codex token events, calls the real archive/collector, then rollup and validated export with the collected entries. Each round loads once and feeds that result to export; it does not replay independently scheduled collect and requested export processes. Each case runs in a fresh child with isolated HOME and state. It measures initial collection, repeated unchanged input and one appended event per changed round. A deterministic synthetic price table exercises the real local cost calculation; price-provider calls are replaced, quota calls are prohibited, socket connections are blocked and only the fixture's local Git identity lookup is allowed as a child process. Exporter clean-tree identity checking is replaced with a synthetic manifest identity so a dirty optimization candidate can be measured; the report records actual source hashes separately. This does not exercise the production exporter identity gate.

The default table shows full-round CPU/wall time and parsed-file counts. `--pipeline rollup` measures the scheduled bucket path without full event export. `--json` retains non-overlapping collection and export/rollup phases, source hashes (including dirty content), environment, accounting checks, archive/result database bytes and worker peak RSS. It also counts decoded archive entries and priced entries; compare work counts as well as timing to distinguish incremental work from a faster full scan. CPU includes reaped children; peak RSS includes setup/readback, excludes children and is not incremental phase memory. Setup, fixture mutation, extra verification and cleanup are outside the timed operation. Export samples verify snapshot event/input/output token totals, zero cache counters and nominal event costs; both modes verify rollup input/output tokens, entry/known-cost counts and known cost totals. Failures exit nonzero. The parent cleans temporary state on the default 120-second per-case timeout; completed cases remain in a failed JSON report. Use `--timeout` to set a different explicit bound.

These synthetic cases expose retained-history growth and input invalidation; they do not represent real log distributions, startup imports, price/quota providers, transport, schedules, idle wakeups or production heat/power. Unchanged input may avoid parsing while still materializing and exporting all history. Compare the same rows/repeats, source hashes and environment before/after; a faster export phase alone does not establish lower total background cost. Tests for the instrument live in `tests/test_benchmark_background.py`. Retain JSON outside temporary directories when using it as evidence; inputs are regenerated by the versioned script.
