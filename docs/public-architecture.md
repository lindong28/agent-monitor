# Architecture

agent-monitor is an independent Python service with a static JavaScript dashboard. Bash entrypoints manage a checkout-local Python environment and runtime. No parent repository, LLM Gateway service or private skill is required.

## Responsibility map

Public shell commands and the documented Python adapters remain at the checkout root. Internal implementations live with their domain under `agent_monitor/`; this is a checkout-based application, not an installed Python distribution. Tests below identify starting points for each responsibility, not every consumer of a shared contract.

| --- | --- | --- |

`agent_monitor/http_server.py` composes HTTP handlers with application views, account memory, quota view and collection coordinator. Overview, session and network query logic lives in `agent_monitor/views/`; session/conversation caches and network result caching belong to those view instances. The coordinator owns scheduling state and query-view admission; account memory owns its lock, deletion epochs and JSON persistence. `quota_sync.Manager` owns recovery exclusion and receipt acceptance/persistence; the HTTP handler keeps that exclusion through response delivery. Shared `file_io` primitives do not merge the distinct account-memory and quota-message durability sequences. Internal components receive dependencies instead of importing `agent_monitor/http_server.py`. `web/app.js` composes shared UI and page modules; see the frontend boundaries below. The [backend cost map](#backend-performance-checks) identifies distinct runtime consumers. `examples/` holds synthetic inputs; root `machines.json` and `hub.json` supply the runtime defaults and customization templates; `scripts/` holds explicit acceptance/measurement tools; `tests/fixtures/` holds test inputs. See [development checks](../CONTRIBUTING.md#choose-a-validation-entry) before running optional tools.

Changes to SQLite connection entry points also require the connection and daily-rollup/ATTACH census tests in `tests/test_storage_source_boundaries.py`. Classify a new or moved entry by its actual read/write, locking and unpublished-staging boundary; retain the domain's runtime tests as evidence for those semantics. The census uses the registered application source inventory plus its explicit diagnostic tools, excluding runtime and vendor trees. Query-view and generation-GC tests share a plain snapshot fixture in `tests/fixtures/rollup_snapshot.py`; HTTP transport tests belong to `tests/test_http_delivery.py`.

### Where new code belongs

Use the responsibility map above as the directory policy. Place a change with the component that owns its behavior or mutable state; a filename or line-count target alone is not a reason to split it. Follow the existing domain when extending it, and update this map when introducing an actual new owner.

| Kind of change | Placement and boundary |
| --- | --- |
| Shared records, validation or constants used by several domains | `agent_monitor/contracts/`; keep imports independent of parsers, ingestion, storage implementations and HTTP. `parsers/__init__.py` re-exports existing model names for compatibility. |
| Source discovery, normalized usage loading, archive enrichment or project identity recovery | `agent_monitor/ingestion/`; the identity store owns its path/cache/lock and the loader owns its usage cache. `agent_monitor/aggregations.py` contains pure computation; loaders and loaded-history types are imported directly from their ingestion/contracts owners. |
| Read-side overview, session or network query behavior | `agent_monitor/views/`; accept explicit dependencies and keep mutable caches on instances. HTTP parsing, response delivery and composition remain in `agent_monitor/http_server.py`. |
| Dashboard page behavior | A page module in `web/`, using the existing factory/lifecycle interfaces. `app.js` owns composition/navigation; page subscriptions and timers belong to the page lifetime. |
| Public invocation and domain implementation | Keep documented public entries as thin adapters. Runtime, snapshots, accounting, accounts, network and quota implementation belongs in its domain package. Independence alone does not justify another root module; do not create a generic utilities owner. |
| Examples, checks and explanation | Synthetic examples in `examples/`, repeatable developer tools in `scripts/`, regression tests/fixtures in `tests/`, maintained explanations in `docs/`. Runtime state and generated dependencies remain ignored. |

When moving code, migrate real consumers, preserve existing public entrypoints and source identity coverage, and retain only compatibility adapters that have callers. Tests should exercise the owner through its normal interface or injected instances, not restore removed mutable module globals or parse implementation text. The [domain ownership decision](adr/20261027-f6b2-domain-ownership.md) records this extraction's scope.

### Why files remain at the root

Root files need a public invocation, bootstrap, shared contract, configuration or conventional repository purpose. Ordinary internal imports use the domain implementation directly. The service manager deliberately executes `deploy.py` and `runtime_rebuild.py` as separate processes: these thin adapters establish the checkout import root, and runtime rebuild must run under an external interpreter that survives replacement of `.venv`.

| Root group | Reason to retain these paths |
| --- | --- |
| `agent-monitor`, `ip-check` | Daily operations and network diagnostics. Shell dispatch lives in `agent_monitor/runtime/`; Python handlers live in their domain packages. |
| `install.sh`, `uninstall.sh` | Installation and integration removal; implementations live in `agent_monitor/runtime/`. |
| `start.sh`, `stop.sh`, `status.sh` | Compatibility commands. Start/stop forward to the dispatcher; status without arguments forwards to `agent-monitor service status`, while its component selectors retain their narrower scope. |
| `deploy.py`, `runtime_rebuild.py`, `upstream_controls.py` | Thin adapters for documented public invocations, including recovery with an external Python when the managed runtime is broken. |
| `project_paths.py` | Checkout bootstrap shared by package and script consumers. |
| `token_cost.py` | Byte-identical cross-project arithmetic contract with an established path. |
| `hub.json`, `machines.json` | Runtime defaults and first-time customization templates; copy to the corresponding ignored local file only when it does not already exist. `examples/` does not duplicate these defaults. |
| `pricing.json` | Bundled accounting price resource consumed by `agent_monitor/accounting/pricing_fetcher.py`, separate from operator configuration and the fetched cache under `state/`. |
| README, license, contribution/security policy, manifests and tool configuration | Conventional repository discovery and tooling; these are not implementation modules. |

`agent_monitor/contracts/` contains dependency-light usage, identity and calendar rules. Ingestion, views, collection and domain packages keep their existing state ownership; moving files does not merge locks or persistence protocols. Package initialization stays lightweight. `file_io.py` provides shared file synchronization primitives, while `quota/quota_messages.py` owns private quota JSON publication. Existing `parsers/`, `ip_check/`, `proxy_runtime/` and `web/` retain their responsibilities. See [the package entrypoint decision](adr/20261028-9e4b-package-entrypoints.md), which supersedes the earlier root-retention rule.

The root shell commands preserve their public names and forward to the runtime owner. `runtime/local_web.py` and the runtime shell scripts call that owner directly; launchd recipes retain the public command for compatibility. `deployment_guard.py` captures the marked body of `runtime/install.sh` under the deployment lock and verifies the source before and after execution. The captured body keeps the public installer path as `$0`, so checkout-relative paths remain stable. `runtime/install_output.sh` only writes optional ledger records to the inherited descriptor; human warnings and command exits belong to the installer.

### Paths are part of runtime identity

`project_paths.py` anchors the checkout independently of the current working directory and internal module location. Its state/resource helpers retain the `state` symlink rather than resolving, creating or replacing it. Internal child processes use package module entrypoints with the checkout on their import path. Service recognition accepts the owned legacy script command and its replacement module form during upgrades; unrelated command lines remain rejected. Internal modules use the shared root; tests can provide explicit roots or component instances.

`agent_monitor/source_inventory.py` registers application package roots once and exposes different views: Python compilation and server drift include runtime Python; service identity also includes proxy CJS, requirements, the Hub marker and selected local/default configuration; exporter clean-source admission uses Git pathspecs for code and accounting resources, excluding operator configuration. CLI compilation, server drift and the refresh client consume the same Python view. The refresh client compares `source_inventory.source_signature` without importing or constructing the Web service. New nested modules inside registered packages are included automatically; a new package root must be registered and verified with `tests/test_source_inventory.py`. Do not replace these views with an unrestricted checkout scan. Preserve public commands, state location, machine identity and the shared `token_cost.py` arithmetic contract when reorganizing code.

### Dependency and state boundaries

| Boundary | Ownership and consumers | When changing it |
| --- | --- | --- |
| Rollup storage | `agent_monitor/storage.py` owns lock identity, thread/file lock registries, fork handling and safe read connections. Rollup and ingestion consume it; storage does not import either consumer. | Run lock/read-connection and identity-recovery tests as well as rollup/aggregator tests. Preserve SQLite/WAL read behavior and one registry. |
| Ingestion | `ProjectIdentityStore` owns identity persistence/recovery; `UsageLoader` owns scanning, archive merging and enrichment. Default instances are composed in `agent_monitor/ingestion/__init__.py`; callers can construct isolated instances. | Preserve identity/rollup lock before loader lock. Archive parser fingerprints include moved implementations and contracts, separately from deployment source inventory. |
| Query views | HTTP composition supplies overview/session/network view instances. Session and network caches stay with their owner; network cache failures and retry lifetime are shared by requests to that instance. | Exercise independent instances, cache reuse, failure/retry and existing query shapes; extraction must not add provider queries or change TTLs. |
| Quota acquisition | `agent_monitor/quota/quota_service.py` owns acquisition/recovery; exporter and Hub supply their role, root and cache options. Exporter compatibility adapters remain for existing callers. | Check standalone, Hub and GUI cache/refresh paths without real provider calls; view tests alone do not cover acquisition. |
| Account memory | One `AccountMemory` instance owns `state/account_memory.json` and concurrent deletion/upsert coordination. Quota views and HTTP deletion use that same instance. | Preserve admission → epoch registration → live candidate derivation; deleting an account must not allow an older in-flight candidate to restore it. |
| Collection | One coordinator owns round state, refresh requests and callbacks; HTTP handlers request or read it. | Check automatic/manual refresh, overlapping requests, completion/failure and query-view lifetime. Extraction does not add collection work or change cadence. |

Runtime data remains under `state/`: archives and rollup preserve usage history, generations hold admitted snapshots, account memory preserves remembered readings, and identity/lock files protect those owners. These are distinct from developer task evidence. [Task storage](../CONTRIBUTING.md#local-task-evidence) describes local evidence navigation; it does not relocate business data.

### Frontend boundaries

The static dashboard uses explicit module factories shared by browser script loading and Node tests. `web/app.js` composes page behavior, navigation and page lifetime; separate modules own overview, collection, charts, quota rendering, network rendering and sessions. The factories receive their dependencies and expose the interfaces tested by Node, so tests do not rewrite source strings to reveal private functions. Route tests use the normal route interface with a DOM fixture. `web/pivot.js` also exposes a factory. Browser globals retained by the page composition remain compatibility surfaces, not independent copies of application state.

HTML loads shared modules through the existing versioned asset delivery. Dynamic account modules propagate the document version explicitly; adding a module dependency must preserve this through the entire loading chain. A page's subscriptions, timers and charts end with that page's lifetime. Validate both initial entry and navigation away/back when changing shared modules; normal imports passing in Node do not establish browser loading or cleanup.

## Usage path

`parsers/claude.py` and `parsers/codex.py` read the operator's agent logs into the shared usage representation in `agent_monitor/contracts/usage.py`. The ingestion loader discovers sources, resolves project identity, merges retained observations and enriches costs. `agent_monitor/ingestion/usage_archive.py` retains normalized observations. `agent_monitor/accounting/rollup.py` maintains daily aggregates with project/source identity and shrink guards. `agent_monitor/snapshots/generation.py` and `agent_monitor/accounting/rollup.py` use constants from `agent_monitor/contracts/rollup.py`, so generation admission does not import the rollup implementation for constants. `token_cost.py` and `agent_monitor/accounting/pricing_fetcher.py` derive known-cost subtotals from recorded tokens and available prices. Missing prices or incomplete counters stay distinguishable from known zero.

`agent_monitor/http_server.py` exposes usage, session, quota, collection and network routes through the composed views. `agent_monitor/aggregations.py` provides pure aggregations; session and conversation caches support session views. `web/` renders them. Codex native subagents can be grouped with their main conversation using explicit ancestry; unresolved ancestry is not guessed. Date boundaries use Asia/Shanghai.

`parsers/codex_profiles.py` independently reads the optional portable registry at `~/.local/share/codex-accounts/NAME/profile.json` (schema version 1). Each valid profile contributes `codex/sessions`, `codex/archived_sessions` and its own `codex/state_5.sqlite`; no module or service from the registry producer is imported. Immutable profile identity supplies optional session `account` metadata (`name`, `account_id`, `email`). The ordinary default Codex source remains supported without retrospectively assigning its sessions to today's login. Conflicting copies of one session ID retain the existing usage deduplication and expose unknown account attribution; cross-account ancestry is not grouped.

Statistics extension version 5 carries optional account metadata and continues reading versions 1–4. Upgrade the Hub/consumer before exporters: an old reader cannot admit version 5 and retains its prior successful generation. Managed profiles also contribute passive quota observations under the existing Codex block's `managed_accounts` array; the server merges these into ordinary account rows by provider account ID and email, never by directory label. Multiple observations from one machine contribute only one machine association per account. These reads do not log in, refresh tokens or query a provider. The dashboard identifies reading sources in the quota update details, separately from account labels, and missing readings remain unknown. Profile identity describes the managed home, not independent proof of a token's validity.

Cross-account resume is recorded by the launcher in `~/.local/share/codex-accounts/session-links/UUID.json`: schema version 1, `storage_account`, `last_selected_account`, and cumulative `account_names` (including storage and selected names). These names record selections, not completed requests or billing. Monitor reads this independent JSON protocol once per collection, without importing launcher code. More than one name makes that UUID's account unknown, including retained metadata whose rollout has disappeared. This metadata transformation runs after archive merging even when usage-file caches are unchanged; it does not rewrite token usage or cost arithmetic. Invalid records produce source errors and unknown attribution for the affected UUID; an unreadable registry or unidentifiable JSON record makes all Codex attribution unknown until repaired.

Default-home and managed-home passive quota collection excludes mixed or invalid UUIDs. Passive quota cache signatures include the exclusion set, and new `quota_observation` values optionally carry `session_id` to reject a cached reading precisely. When exclusions exist, older passive cache records without a UUID cannot be verified and are withheld; active-query observations and their account identities remain valid. Existing account-history snapshots remain historical observations, not evidence of which account paid for a resumed turn. Registry changes do not alter provider refresh scheduling or pause/recovery policy. No statistics schema upgrade is required beyond version 5's existing nullable account metadata.

Ancestry resolution remains scoped to each Codex home. A child rollout in another home whose `history_base` references the source home can report `history_base parent missing or ambiguous`; without an independent last-usage observation, its inherited cumulative usage cannot be counted safely. This limitation is demonstrated by a synthetic fixture, not a claim that every native resumed child produces this shape. A target-home rollout without that cross-home dependency is still collected even if its SQLite index lives elsewhere.

## Multiple machines

`agent_monitor/snapshots/machine_config.py` validates named machines, SSH targets, the local role and retired identities. At startup it selects `machines.local.json` if present, otherwise `machines.json`; explicit caller paths remain explicit. `agent_monitor/hub_config.py` owns the same local-over-default convention for Hub configuration, the installed machine marker and read-only role/interval rules; `agent_monitor/runtime/hub.py` composes the CLI and service lifecycle. All importers share the selected machine path, including retirement writes. Adding or removing a local configuration file requires restarting processes.

`agent_monitor/snapshots/exporter.py` produces versioned snapshots from a committed, clean source tree. `agent_monitor/snapshots/sync.py` invokes the installed exporter on declared SSH hosts; `agent_monitor/snapshots/generation.py` verifies and admits immutable snapshot generations. `agent_monitor/views/query_view.py` prepares admitted aggregates for repeated API reads and keeps leases while consumers use a generation. Old snapshots remain distinct from newly observed quota readings. Raw provider secrets stay on their owning machines.

The optional Hub marker in `state/hub-machine` enables role-specific behavior. macOS LaunchAgents provide periodic local collection and the Hub service. Standalone mode works without a Hub marker and does not contact the maintainer's fleet in the exported public candidate.

## Network and account actions

`agent_monitor/network/network_policy.py` and `proxy_runtime/` use a pinned Electron helper for Chromium system-proxy resolution. This helper is installed locally; it is not a hosted gateway. `agent_monitor/network/network_report.py` and `ip_check/` perform explicitly requested diagnostics, separate from log accounting.

`agent_monitor/accounts/codex_accounts.py`, `agent_monitor/accounts/codex_messages.py`, `agent_monitor/network/client_network.py` and `agent_monitor/network/client_connector.py` implement optional account actions and paired browser-device routing. Login and sending require their own actions. Current-account quota refresh can run automatically when opening the dashboard or reading the standalone overview; explicit refresh also requests it, and Hub collection uses its configured schedule. These queries use existing account state and do not generate a model turn. Unknown send outcomes are retained and are not automatically replayed. `upstream_controls.py` retains local provider pauses. Live provider behavior is not established by synthetic sample data or unit tests.

## Persistence and maintenance

Runtime state is under `state/`, which may be an existing deployment-owned symlink. Preserve identity files, locks, archives, account profiles and retirement records during upgrades. `.venv`, `.runtime`, `web/vendor`, local configuration and state are not publication artifacts. Generated caches are not substitutes for authoritative retained history.

Choose storage maintenance by the consumer's task, not by whether a file is called a cache:

| Data family | Purpose and lifecycle |
| --- | --- |
| Retained raw usage | Historical usage and cost queries survive disappearing source files. There is no automatic history expiry; deleting it changes those queries and the available facts for recalculation. |
| Source observations | Preserve source-specific observations for deduplication and corrections. Removed sources lose their observations while retained usage survives. Paths are normalized; distinct observations remain distinct. |
| Prepared contributions and rollup | Persistent incremental state avoids repricing and reaggregating all history. Keep compact prior contributions; invalidate affected keys/models/projects. Missing state or calculation-version changes can require a full rebuild, so periodically clearing it increases repeated work. |
| Session/conversation query caches | Reusable read results, bounded by entry count and bytes (each defaults to 16 MiB). Eviction recomputes the requested view; it does not expire historical facts or reset incremental accounting. |
| Published generations | Current, previous and actively leased generations support reads and recovery. Generation GC protects those consumers; deleting a live generation is not cache maintenance. |

Logical compaction can leave reusable SQLite pages without shrinking the file. The explicit [archive maintenance command](public-usage.md#configuration-and-retained-data) performs physical compaction with a verified backup and the existing writer lock. Report archive reduction and retained backup occupancy separately. Ordinary service logs and one-transfer staging have their own lifecycle; neither determines the retention of usage history.

Local sync staging uses a registered directory and kernel lease. The next sync can reclaim an abandoned directory only when its ownership protocol is recognized and no producer or transfer still owns it. The local transfer guardian retains the lease across parent termination; an unfinished transfer whose completion cannot be established is preserved. Legacy directories, unknown markers and changed identities are retained with a bounded summary of reasons and examples, while a healthy active lease is not reported as a fault. There is no age-based deletion or additional cleanup daemon. See the [staging lifecycle decision](adr/20261028-4424-sync-staging.md); remote transfer and published-generation retention remain separate.

Backend work should inspect the actual affected consumer: aggregate preparation, retained-session reads, snapshot publication, sync and quota operations have different costs. Repeated view preparation and generation invalidation have regression tests in `tests/test_query_view.py`; `scripts/benchmark_backend.py` uses synthetic snapshots. Those observations do not establish production latency for other paths.

See [usage and operations](public-usage.md), [contributing](../CONTRIBUTING.md) and the module tests before changing these boundaries.

## Implementation constraints and tradeoffs

HTTP binding does not perform reverse DNS. Browser action admission accepts the existing IP and local-hostname cases without reverse DNS; other hostname aliases still use the host's FQDN lookup. Origin, action-header and cross-site checks remain required. A slow resolver can still delay requests using those other aliases.

`agent_monitor/asset_delivery.py` binds static resource URLs to the Web tree's path-and-content signature, including a symlinked vendor directory. HTML remains uncached; matching versioned resources can be reused in the browser without a validation round trip. Unversioned or obsolete URLs retain conditional validation. Dynamic account modules carry the document's version, and the existing health watcher reloads a document when its Web signature changes. Text responses and aggregate JSON negotiate gzip when it reduces bytes; API results remain `no-store`. The bounded in-process byte cache invalidates on file identity, size or timestamp changes; it does not persist usage data. See the [delivery decision](adr/20261026-8d31-dashboard-delivery.md).

Statistics export copies only mutable usage metadata and formats timestamps directly. It validates and encodes every usage row before opening the destination, retaining encoded rows rather than both row dictionaries and a second encoded batch. Within one private staging export, the published manifest reuses that operation's actual readback, rollup statistics and digest, with file-identity checks before publication. These facts are local to the call; public validation and receiving admission still inspect the actual files. Snapshot schema, row order and post-write validation are unchanged. Export still processes the full retained history; this reduces repeated serialization/validation work, not collection frequency or snapshot size. Rollup reconciliation likewise keeps complete prepared buckets for replay, but writes only changed buckets and deletes obsolete keys within the permitted authority scope; unchanged buckets incur no row writes. See the [work reuse decision](adr/20261028-4424-export-work-reuse.md).

Usage enrichment creates one `PreparedPricing` per collection. It reuses exact-model lookup results and supplies only the shared calculator's six rate families (including threshold variants) to arithmetic, while retaining the original catalog for model admission, service modes, regional multipliers and provenance. `token_cost.py` remains the shared arithmetic authority; changes to its consumed rate families must also update this preparation and its equivalence tests in `tests/test_prepared_pricing.py`.

The archive stores source observations by file and event key, with each source path stored once in a dictionary. Changed files replace their observations and replay only affected keys; unchanged files do not decode their cached events. SQLite triggers persist dirty keys for every raw-event insert, update and deletion, including writes by older code. Source deletion removes its cache, never retained usage facts. Version-marked signatures force older collectors to reparse instead of trusting the empty compatibility payload. Archives predating incremental observations need an initial source-cache rebuild; the path-dictionary migration reuses existing v1 observations and valid signatures. The empty legacy observation table and its write triggers retain downgrade compatibility; an older writer's changes invalidate the affected paths on re-upgrade. See the [path normalization decision](adr/20261028-4424-normalized-observation-paths.md).

`accounting/usage_projection.py` keeps the previous bucket contribution and derived field overlay in the raw collection transaction. It reconstructs complete events by joining raw facts with that overlay; correction or deletion can still withdraw the previous contribution independently of the changed raw row. Calculation-source changes and missing derived state rebuild from retained facts. Pricing/provenance changes invalidate only models whose resolved, ordered price record or source changed; `ingestion/usage_models.py` maintains raw-model counts and an indexed lookup, including older writers. Project mapping/blocker changes similarly use a raw-project index. Unrelated prices or projects do not reprice history. `accounting/usage_buckets.py` owns the shared event-to-bucket arithmetic; full and incremental sums use exact binary contributions to avoid subtraction drift and consumer-dependent rounding. Ordinary rounds replace contributions only for changed keys, and empty buckets disappear. This state survives independent CLI processes; a downstream rollup failure can retry using complete prepared buckets. Scheduled `rollup` uses `UsageLoader.load_rollup_entries`, while full-history readers and exports still materialize complete events. Read-only diagnostics retain their existing scan/enrichment path. Codex's current thread-model mapping refreshes session metadata but does not invalidate historical usage, whose model comes from source records. See the [incremental collection](adr/20261028-4424-incremental-collection.md), [compact projection](adr/20261028-4424-compact-usage-projection.md) and [price dependency](adr/20261028-4424-local-price-invalidation.md) decisions.

This is not a delta-only scanner: discovery and source signatures scale with file count, metadata/header work with sessions and the Codex database, changed-file reparsing with those files' complete contents, and reconciliation with bucket count. Full exports still serialize and validate retained history. Raw history and derived caches grow with retained events; no retention or freshness policy changed. An unchanged round does not rewrite the archive; invalidation and the first upgraded round can be substantially more expensive than a warm round.

Standalone schedules call `rollup`; they do not use the dashboard-dependent `refresh` path. Hub `collect` and requested exports both retain their local rollup work. Reusing a recent export by skipping a collector when observation age is less than interval I would weaken the collection bound: collection at 0, export at ε, skipped collection at I, then a disconnected Hub can leave the next collection until 2I. Safe reuse would need scheduling against the actual observation deadline, completeness and identity checks, and continued collection when transfer stops. The current implementation preserves independent collection; no CPU, I/O or process-count savings have been measured for reuse.

Rollup also reaches this resolver through `UsageLoader.load_all_entries` → `pricing_fetcher.get_pricing` when price data needs refreshing. Removing Electron from a collector-only installation would change pricing fallback behavior. The installer therefore keeps one dependency set rather than adding role-specific installation modes and their maintenance burden. Local rollup is not an offline guarantee.
